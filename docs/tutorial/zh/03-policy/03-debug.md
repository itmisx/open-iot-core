# 排查被拒绝的请求

连接或订阅被拒绝时不应依靠推测。控制台的策略调试器直接给出判定过程：命中的语句、各变量的求值结果，以及放行该请求尚缺的条件。

## 使用策略调试器

入口位于导航中的「策略调试器」。需填写三项：

1. 策略（下拉选择，默认选中第一条）
2. 动作与主题（或 clientId，取决于所选动作）
3. 设备名（可选；含设备变量的策略须依此求值）

判定结果会给出命中语句的下标。无语句命中时结果为「隐式拒绝」——这不是故障，而表示策略中没有任何一条许可该操作。

调试器仅依据**策略文档**判定，不要求选择主体类型：某台设备所使用的策略，在设备页与证书页上已直接标明。

## 常见现象与成因对照

| 观察到的现象 | 主要成因 |
| --- | --- |
| CONNECT 被拒绝，证书无异常 | clientId 不等于设备名（起步策略将资源限定为 `client/<设备名>`） |
| 订阅成功但收不到任何消息 | 放行了 `iot:Subscribe`，未放行 `iot:Receive` |
| SUBACK 直接失败 | 过滤器不在 `topicfilter/` 的放行范围内 |
| 所有操作均被拒绝，策略看似正确 | 证书未绑定设备，含设备变量的语句整条拒绝 |
| 某条策略似乎未生效 | 资源中使用了 MQTT 的 `+`，它在 IAM 风格匹配中不是通配符 |
| 策略已修改但设备行为未变 | 策略集在 CONNECT 时解析一次，既有连接须重连后方按新策略判定 |

## 借助事件流回溯

每一次授权拒绝均记录为一条事件，其中包含被拒的动作、主题与命中情况。导航中的「事件流」可实时查看，设备页的时间线则按设备汇总历史记录——「设备为何在凌晨掉线」这类问题可在该处得到依据。

拒绝事件支持一键回放至调试器，无需手工转抄主题，因而不会引入抄写错误。

## 变更策略前的注意事项

收紧策略会中断正在运行的设备，但不会立即生效：策略集在连接建立时解析一次，已连接的设备须等到重连才会受新规则约束。因此「变更后观察无异常」与「设备在夜间陆续掉线」是同一事件在两个时刻的表现。在调试器中针对真实主题预先验证，成本显著低于下发后再回滚。
