# 合并语义、版本与删除

影子共有六条规则，而每一条被误用时的现象都不指向其成因。本页将六条规则与各自的现象并列说明。

## 更新为深度合并，而非整体替换

`update` 仅修改请求中出现的键，未出现的键保持原值。因此下列更新不会移除 `mode`：

```json
{ "state": { "desired": { "interval": 60 } } }
```

若将其误解为整体替换，调用方通常每次提交完整文档。该做法本身可以工作，但两个客户端并发写入时会相互覆盖——各自提交的都是「自身视角下的全文」。

## 删除字段须显式写入 `null`

```json
{ "state": { "desired": { "mode": null } } }
```

`null` 表示删除该键，而非将其置空。未找到删除方式时，调用方常改为提交空对象 `{}`，而空对象不产生任何效果——合并一个不含键的对象，结果与原文档一致。

## `version` 实现乐观并发控制

请求中携带 `version` 表示「本次修改基于该版本」：与当前版本不一致时返回 409，本次写入不生效。省略 `version` 则无条件接受。

```json
{ "state": { "desired": { "interval": 60 } }, "version": 7 }
```

两名运维人员并发下发不同取值时，省略 `version` 的一方将无提示地覆盖另一方。409 的含义是「请先读取再修改」，不属于故障。

## `delta` 是差集，而非最近一次写入的内容

节点逐叶子比较 `desired` 与 `reported`，取值不一致的部分构成 `delta` 并下推至设备。由此有两项推论：

- 设备按 delta 调整后**必须上报 reported**，否则 delta 将持续存在。
- `desired` 与 `reported` 一致时不产生 delta。下发与当前值相同的期望状态后设备无任何动作，这不属于消息丢失。

`update/documents` 提供的是另一类信息：本次更新前后的完整文档对照，用于审计与问题排查。

## 删除后版本号重置

`delete` 移除整份文档。此后重新创建的影子自版本 1 开始计数。

使用删除前获取的 `version` 发起写入将返回 409。编写自动化脚本时，应或省略 version，或先执行一次 `get` 取回当前版本。

## 文档限额

| 限制项 | 取值 | 超限时的处理 |
| --- | --- | --- |
| 文档大小 | 8 KB | 拒绝整次更新 |
| JSON 嵌套深度 | 8 层 | 拒绝整次更新 |
| 影子名长度 | 64 字节 | 拒绝 |
| `clientToken` 长度 | 64 字节 | 拒绝 |

影子不是时序存储：将历史采样写入 `reported` 最终会触及 8 KB 上限，而外部现象是「某次更新失败」，并不提示选型有误。历史数据应经消息流存储。

## `clientToken` 原样回传

请求中携带 `clientToken` 时，`accepted` 与 `rejected` 响应将原样回传该值。单台设备存在多个并发请求时，须依此将响应与请求配对——应答主题只有一个，自身不区分请求来源。

## 设备收不到应答时优先核查策略

影子的全部主题均位于 `$aws/things/<设备名>/` 之下。起步策略已放行该子树；自行编写策略时遗漏 `shadow/` 某一段的现象是「可以发出，收不到应答」。详见[访问策略](#/guide/policy/basics)。
