# 08 证书与 CA 生命周期

## 1. 关键设计决策

| ID | 决策 | 状态 |
| --- | --- | --- |
| PKI-001 | 吊销不以 CRL 或 OCSP 为主路径。证书状态存于元数据组，握手时查本地热视图。 | v0.1 |
| PKI-003 | CA 私钥不进入 Raft 日志、WAL 或快照。符合 CLU-028。 | v0.1 |
| PKI-004 | 签发为特权角色，仅 `signer` 角色节点持有密钥。符合 CLU-029。 | v0.2 |

PKI-001 的理由：CRL 分发对 IoT 场景不适用（设备数量大、离线频繁、CRL 体积增长不可控），
而证书状态查询在本地热视图中是约 50 纳秒的 map 查找。

## 8. 格式冻结项

实现 `internal/pki` 与 `internal/broker/listener.go` 期间确认：下列字符串格式
一旦发布就不能再改，因为它们被 IoT Policy 以**字符串精确匹配**引用。
改动不会报错，只会让所有引用该变量的策略静默失效——这是最难排查的一类故障，
故在此冻结。

| ID | 需求 | 状态 |
| --- | --- | --- |
| PKI-100 | `${iot:Certificate.SerialNumber}` 的格式冻结为：序列号大端字节串（去掉前导全零字节）的小写十六进制，无分隔符。因此长度恒为偶数。序列号为零时取 `"00"`。注意这**不是** `big.Int.Text(16)`——后者会产出奇数长度，两者对约 6% 的 128 位随机序列号结果不同。 | v0.1 |
| PKI-101 | `${iot:Certificate.Subject.CommonName}` 等主题字段取自证书的 DN，不做任何规范化（不改大小写、不去空白）。 | v0.1 |
| PKI-102 | 证书指纹冻结为证书 DER 的 SHA-256，小写十六进制。注册与认证两侧必须用同一算法；不一致时表现为「证书未注册」，错误信息指不出真因，故须有专项测试锁定（见 TST-095）。 | v0.1 |
| PKI-103 | 分层 CA 部署下，服务端与设备证书均须呈现到根的完整证书链。只发叶子证书会以「未知签发者」失败——这是分层 CA 最常见的部署错误，须在文档与示例中显式说明。 | v0.1 |

## 签发的 HTTP 入口（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| PKI-104 | 签发须有 HTTP 入口，不得只有 CLI。只有 CLI 意味着加一台设备必须登到服务器上，控制台最常用的那件事做不了。 | v0.1 |
| PKI-105 | 两条路径须是**两个端点**（`/certificates/issue` 与 `/certificates/sign-csr`），不得合成一个按字段分支。二者的安全性质完全不同，而"少传一个字段就从不传私钥变成传私钥"是最容易出事的隐式行为；路径里写明做的是哪件事，调用方不会搞错。 | v0.1 |
| PKI-106 | 两个端点须互相指向对方：往 `issue` 传 CSR、或 `sign-csr` 不带 CSR，都要拒绝并在提示里给出正确的端点。 | v0.1 |
| PKI-107 | 签发后立即生效，不需重启节点。登记走 `registry.PutCertificate`（先热视图再冷层），与吊销（PKI-030）是对称的两个方向。 | v0.1 |
| PKI-108 | 登记失败时**整体失败**，不得把证书返回给调用方。一张签出来但没登记的证书连不上，而调用方会以为它能用，于是去排查设备侧——真正的问题在服务端。 | v0.1 |
| PKI-045 | 管理监听器是明文 HTTP（无 TLS 选项）。绑在非回环地址时须拒绝经 `issue` 返回私钥，并在提示里指向 CSR 路径。令牌保护的是访问权限，不是传输机密性。 | v0.1 |
| PKI-046 | 放宽 PKI-045 须单独的 `acknowledge_plaintext_key_export`，不得复用 `acknowledge_public_exposure`。合并会让一个只想开管理面的人顺带获得明文导出私钥的能力。 | v0.1 |
| PKI-047 | 未绑定策略或设备不存在时须在**签发时**拒绝。允许签发一张注定连不上的证书，会把失败推迟到设备第一次连接，且那时的拒绝原因含义模糊。 | v0.1 |
| PKI-048 | 审计记证书指纹与设备名，**不记**私钥与证书内容（NFR-041、OBS-054）。须有测试在日志里搜私钥正文（`TestIssueDoesNotLogPrivateKey`）。 | v0.1 |
| PKI-049 | EC 的 CSR 若以"显式参数"编码曲线，Go 的 x509 解析不了，报出的是 `invalid ECDSA parameters`。该失败与签发策略无关，须给出针对性提示（重新生成 CSR 的完整命令），不得落到"见 issue_policy"的默认提示上——这类误导比没有提示更费时间。 | v0.1 |

## 绑定变更的断连语义（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| PKI-109 | 证书的设备绑定被**改动或清除**时，须断开所有在用该证书的活连接。这是 PKI-030（吊销即时断连）的同一类：连接的 `${iot:Connection.Thing.ThingName}` 在握手时解析并固定，改绑之后旧连接仍以旧设备的身份收发——凭据已经移走，权限却留在原处。运维做的是"把这张证书给另一台设备"，不会预期旧设备还能继续用它。 | v0.1 |
| PKI-110 | 原绑定为空时**不**断连。那样的连接在握手时就解析不出设备变量，`AuthzCtx` 已固定为"无设备"，新增绑定不会让它多拿到任何东西。 | v0.1 |
| PKI-111 | 证书此前已不可连接时不断连：那种状态下没有活连接需要处理，它们在状态变更时已被断开。 | v0.1 |
| PKI-112 | 吊销与改绑同时发生时仍须断连。两条判定不得互相短路——先判出"状态仍可连接"就返回假的写法会漏掉这一情形。 | v0.1 |
| PKI-054 | 断连判定（`Change.RequiresDisconnect`）须有真值表测试。两个方向都错不起：漏判是安全问题（凭据已移走而权限还在），误判是可用性问题（一次无关的写入把全网设备踢掉）。 | v0.1 |

## 私钥 PEM 编码（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| PKI-055 | 签发返回的私钥须用设备 SDK 实际吃得下的 PEM 编码：ECDSA 用 SEC1（`EC PRIVATE KEY`），RSA 用 PKCS#1（`RSA PRIVATE KEY`），Ed25519 没有传统格式故用 PKCS#8。AWS IoT Device SDK（awscrt）在 Apple 平台上加载不了 PKCS#8 的 EC 私钥，报 `AWS_IO_FILE_VALIDATION_FAILURE`——一条完全指不到"密钥编码"的错误。AWS IoT Core 自己签发的也是传统格式。 | v0.1 |
| PKI-056 | 读取侧须继续接受 PKCS#8、SEC1 与 PKCS#1 三种。换编码不得让已经发到设备上的旧私钥失效，否则一个兼容性修复会变成一次破坏性变更。 | v0.1 |
| PKI-057 | 编码须由测试断言 **PEM 块类型本身**，不能只断言"自己发的自己能解析回来"。后者永远会过——PKI-056 要求解析侧三种都收——因此它钉不住这件事。原先的测试正是这么写的，所以这个缺陷在 Go 侧完全不可见。 | v0.1 |

### 由来

这条是真实设备对跑（`tests/device-sdk/`）发现的：签发一切正常、Go 测试全绿、
设备连不上，而错误信息里没有任何线索指向私钥格式。它属于"只有换一套真实
客户端才会暴露"的那一类——自己拼客户端验证的是"我以为的协议"。

### 由来

实测复现：把在用的证书从 thing-a 改绑到 thing-b 之后，原连接**仍以
thing-a 的身份订阅成功**。`RequiresDisconnect` 当时只认状态跃迁与删除，
不认绑定变化。

这个缺口在加入关联操作之前就存在（`PutCertificate` 本来就能改 `Thing`），
只是没有入口去触发它。加入 REG-060 等于给它配了一个方便的触发器，所以
两件事必须一起做。
