# 01 语言与运行时选型

## 1. 决策

实现语言为 **Go**。备选方案为 Rust，已评估并否决。本节记录理由与反转判据，
以便范围或指标变化时重新评估，而不必重做分析。

| ID | 决策 | 状态 |
| --- | --- | --- |
| LANG-001 | 实现语言为 Go，最低版本 1.24。 | v0.1 |
| LANG-002 | 不引入 CGO。所有依赖须为纯 Go，以保证交叉编译到 ARM。 | v0.1 |
| LANG-003 | 不采用 Go 主体加 Rust FFI 的混合方案。 | v0.1 |

## 2. 理由

### 2.1 工作量分布

MQTT broker 本体约占本项目代码量的 15%。其余为控制面、影子语义、
Admin API、管理后台、可观测性，特征是大量相互关联的可变状态与直白逻辑。
Rust 的优势集中在前 15%，其所有权模型的成本集中在后 85%。

### 2.2 风险最高的子系统支撑最好

集群层是本项目风险最高的子系统。Go 侧 dragonboat 提供多组 Raft、节点间传输、
Pebble 日志存储的完整打包。Rust 侧 raft-rs 已进入维护模式，openraft 的 0.10 线仍在 alpha，
且两者均仅提供共识核心，传输层、存储层、多组调度器需自建。

选择 Rust 会使风险最高的子系统同时成为生态支撑最薄的子系统。

**修订说明（2026-10-31）**：这一条的论据要收窄。本条原文说"Rust 侧两者均仅提供
共识核心，传输层、存储层、多组调度器需自建"，而 v0.1 与阶段 B 的实际走法是
**自己写了一套单组 Raft**，也就是把"选 Rust 的代价"自己付了一遍——于是这段话
不能再原样当作否决 Rust 的理由。换成 hashicorp/raft（LANG-014 修订）之后，
仍然成立的是**多组**那一半：raft-rs 与 openraft 在多组调度、共享传输与心跳
合并上没有等价物，而那正是 v0.4 分区组要用到的部分。

由此本条的权重变化要写明：若最终不需要分区组（单组吞吐一直够用），本条的权重
归零，语言决策就只靠 §2.1（85% 的代码不是 broker）、§2.3（PKI 在标准库且有
step-ca 这个参考实现）与 §2.4（贡献者池）支撑——仍然指向 Go，但理由少了一条。
另一条不随语言改变的事实：自己实现 Raft 的正确性风险与语言无关，换成 Rust
要写的是同样的那几千行。

### 2.3 PKI 是招牌功能且 Go 明显更完整

证书签发与吊销管理是本项目的核心差异点。Go 的 `crypto/x509` 与 `crypto/tls` 在标准库、
经过审计，PKCS#11 绑定成熟，并有 step-ca 这一成熟参考实现。
Rust 的 rustls 在 TLS 侧优秀，但签发侧为拼凑状态，无 step-ca 等价物。

### 2.4 贡献者池决定项目能否成为行业实现

IoT、cloud-native、基础设施运维人群以 Go 为主。一个无法被贡献的项目不会成为标准实现。

### 2.5 Rust 的主要优势可由部署层决策获得

Rust 在每连接内存上领先 2–5 倍，而该差距的主要来源是 `crypto/tls` 的每连接缓冲。
TLS 可以外移终结（HAProxy、nginx 或独立代理），使 Go broker 处理明文连接，
每连接内存下降 3–5 倍。该手段不需要更换实现语言，而 Go 在集群层与 PKI 的优势无法以部署手段换取。

## 3. Go 的已知劣势与应对

以下为硬性设计约束，不是可选优化。违反其中任一条即否定本节的语言决策。

| ID | 约束 | 针对的劣势 |
| --- | --- | --- |
| LANG-004 | 订阅树使用无指针索引化 arena：节点存于 slice，以 `int32` 索引互指，不使用指针。 | GC 扫描成本随订阅数线性增长 |
| LANG-005 | 每连接最多一个读 goroutine，写出走共享 writer 池。禁止每连接两个 goroutine。 | goroutine 栈内存 |

### LANG-021 的修订：为何不是 Pebble

本条原先定为 Pebble（与 LANG-014、CLU-002 一致）。实现期实测后改为 bbolt：

| 项 | Pebble | bbolt |
| --- | --- | --- |
| 构建图第三方模块 | 26 | **2** |
| 体积增量 | +15 MB | **+1.4 MB** |
| 是否引入 `getsentry/sentry-go` | 是，且**无法去除** | **否** |

决定性的一条是 sentry：`cockroachdb/errors` 的**根包** `report_api.go` 在其全部版本
（v1.10 至 v1.14）都 import sentry，而 Pebble 必须依赖该库。实测它确实被链接进二进制
（37 个符号）。虽然唯一会发送数据的调用点 `errors/report` 不在构建图中、二进制内也无
任何上报地址，但对一个自建的安全产品而言，"引入一个无法去除的错误上报 SDK"本身
就是需要向用户解释的事。用 `replace` 打桩可以绕开，但会破坏 `go mod verify` 与
可复现构建，对在意供应链的项目不可接受。

原先支持 Pebble 的两条理由在重新检视后都不成立：

- **"dragonboat 用 Pebble 做日志后端，可共用引擎"**。这是 v0.4 的事。而 LANG-014 已
  写明后备共识方案是 hashicorp/raft——其标准日志存储 `raft-boltdb` 正是 bbolt。
  选 bbolt 反而与后备方案对齐。
- **"CLU-003 要求快照为 Pebble SST checkpoint"**。该条的真实诉求是"百万设备量级的
  快照不得先读进内存"。bbolt 的 `Tx.WriteTo` 在一个读事务中把整个库文件流式写出，
  内存占用与库大小无关，同样满足，且实现更简单（快照即一个可直接打开的库文件）。

bbolt 的真实劣势是高写入速率下的写放大（B+ 树的写时复制对比 LSM）。影子写入受
QTA-063（每 thing 20/秒）与 QTA-065（全局 4000/秒）约束，且本实现对非关键写入走
`db.Batch` 合并提交，当前规模下不构成瓶颈。若将来实测触及上限，`KV` 接口使更换引擎
仍是模块级改动。
