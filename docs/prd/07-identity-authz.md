# 07 身份与授权

## 1. 定位

本章是项目的核心差异点：策略在进程内求值，零回调、零网络跳。
契约 05 保证该路径不触网，契约 11 保证判定过程可被控制台回放。

| AUTH-067 | 「未登记」「已吊销」「未激活」「待激活」对外须返回同一原因码，使外部无法据原因码探测某个指纹是否已登记。四者的区分只出现在本节点的事件与审计中（AUTH-013）。 | v0.1 |

AUTH-066 修正了一处实现缺陷。原先返回 0x85 有两个问题：

- **语义错误导致排查方向错**。0x85 的含义是"你的 clientId 不对"，
  而真正的问题是这张证书没有被登记。设备接入失败是最常见的运维场景，
  它的原因码直接决定第一步往哪里查。
- **泄露更多**。与"已吊销"用不同的码，等于把原因码变成了一个
  探测指纹是否已登记的接口。

## 起步策略（实现期补充）

`openiotd init` 写出一份名为 `device-scoped` 的示例策略。它不是装饰，
是绝大多数用户的第一份、而且往往是唯一一份策略，因此它的形状会被照抄。

| ID | 需求 | 状态 |
| --- | --- | --- |
| AUTH-068 | `init` 须写出一份可用的设备域策略，不得留空目录。空目录会让新用户卡在"证书签出来了但连不上"，而原因是没有任何策略可绑。 | v0.1 |
| AUTH-069 | 起步策略只放行一条前缀：`$aws/things/<设备名>/*`，发布、订阅、连接（clientId 必须等于设备名）都收敛在它下面。它同时覆盖两类主题——影子等保留主题由 `ReservedService` 处理，其余子主题（`$aws/things/<设备名>/telemetry` 之类）在 `HandleReserved` 返回 `ok=false` 之后落回普通路由，所以第一次业务发布与订阅一样能成功，用户不会卡在"连上了但发什么都被拒"。**修订说明**：原文另外放行 `devices/<设备名>/*` 作为业务分支，现已去掉——两条前缀就要解释"什么时候用哪条"，而设备域的全部能力在一条下面已经齐了；示例策略的首要职责是示范**形状**，少一条前缀也少一处要讲清的东西。形状的关键仍是按设备名分层，而不是 `sensors/temp` 这样的平坦主题：平坦主题无法按设备收敛，任何设备都能读写同一个主题，策略变量就失去意义了。 | v0.1 |
| AUTH-070 | 业务分支按设备名分层，**不得**示范 `sensors/temp` 这类平坦主题。平坦主题无法按设备收敛——任何设备都能读写同一个主题，策略变量就失去意义。起步策略会被照抄，它必须直接示范对的那种形状。 | v0.1 |
| AUTH-071 | 起步策略须有测试直接断言它放行什么、拒绝什么，断言项与 `init` 输出里列出的放行范围逐条对应。一份不生效的示例策略比没有更糟：用户会以为自己用错了，而真正错的是我们发出去的那份文档。 | v0.1 |
| AUTH-064 | 该测试须包含"设备未绑定"的分支：带设备变量的语句此时一条都不能放行（AUTH-036）。否则 `$aws/things/${ThingName}/*` 会退化匹配 `$aws/things//*`，而后者是攻击者可自由构造的主题。 | v0.1 |
| AUTH-065 | `init` 的输出须直接列出放行范围，并点明两种最常见的被拒用法（随机 clientId、平坦主题）及其排查入口。这是用户见到的第一屏，提示放在这里的收益最高。 | v0.1 |

### 为什么不把起步策略放宽成 `client/*` 与 `topic/*`

那样确实谁都能连上，代价是示范了一份没有任何隔离的策略，而它会被照抄到
生产环境。起步策略的职责是让第一次尝试成功**并且**形状正确；两者冲突时
优先后者，用提示文案补齐前者——即 AUTH-065。

## SigV4 验签（实现期补充）

验签逻辑必须和 AWS 逐字节一致（AUTH-002），否则 boto3 签出来的请求会
被当成密钥错误。下面几条是规范留白、实现时必须定下来的部分。

| ID | 需求 | 状态 |
| --- | --- | --- |
| AUTH-072 | 没有 `X-Amz-Expires` 时，签名时刻与本节点时钟的偏差不超过 15 分钟，双向都算。这是 AWS IoT 对设备时钟的容忍。更短会把只是慢了几分钟的设备全部拒掉；不设上限则一张签过名的请求可以永远重放。 | v0.1 |
| AUTH-073 | 带 `X-Amz-Expires` 的预签名从签名时刻起算，到时刻加这段秒数为止，早于时刻也无效。秒数上限 7 天。没有上限的话，一个写成几十年的链接就永远有效。 | v0.1 |
| AUTH-074 | 凭证范围里的区域与服务名必须落在本节点的配置里。允许的服务名是控制面 `iot`、数据面 `iotdata`、WebSocket `iotdevicegateway`。区域或服务列表为空时拒绝一切，不得默认放行。 | v0.1 |
| AUTH-075 | 请求里出现的 `x-amz-*` 头必须列入 SignedHeaders。漏签的头可以在签名之后被改写，而那些头正是日期、内容哈希和令牌。密钥不存在与签名不对，对客户端是同一个拒绝。 | v0.1 |
| AUTH-076 | WebSocket 验签通过后，access key 写在连接的传输事实里，认证器按它找到设备，策略取该设备已附加的策略集。没有策略就拒绝 CONNECT。密钥和「钥匙对应哪台设备」放在节点本地的密钥文件，启动时读取，不进元数据复制日志。有 access key 但绑不上设备时不得退回证书认证。**适用范围说明**：本条只管设备钥匙。控制面的 access key 已改为存进复制的元数据（AUTH-086）；设备钥匙没有跟着搬，因为它在连接路径上，而那条路径不许有磁盘 IO（AUTH-010）。 | v0.1 |
| AUTH-077 | 规范路径按原始请求的分段边界编码：段内的 `%2F` 在原始串里不是斜杠，不得被当成新的一段。编码对**已编码的那一层再编一次**——AWS 的 SigV4（除 S3）对路径编两遍，线上的 `cert%2Fab` 在签名里是 `cert%252Fab`。两个官方 SDK 各自都这么做（botocore 的 `quote(path, safe='/~')`、aws-sdk-go-v2 的 `rest.EscapePath(GetURIPath(url), false)`）。**修订说明**：原文写的是「先还原再按段编码，结果仍是 `%2F`」，即只编一次。那条规则是推断出来的，不是对着真 SDK 量出来的，而后果是两类请求对任何 SDK 都 401：数据面的 `Publish`（主题整段进路径，`demo/topic` 在线上是 `demo%2Ftopic`），以及控制面凡把 ARN 放在路径里的操作（`ListAttachedPolicies`、`ListTargetsForPolicy`）。它能一直活着是因为包内用例自己构造规范请求再自己验，两边同一套错规则；而 401 的字面意思是密钥或时钟有问题，不指向编码——AUTH-075 刻意把「密钥不存在」与「签名不对」合成同一个拒绝，代价就是这类缺陷的现象与真因无关。现由 TST-145 用真 boto3 覆盖。 | v0.1 |

## 登录方式收敛（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| AUTH-080 | 控制台登录只有一种方式：管理面令牌。OIDC 登录连同它签发的内存会话 cookie 整条移除（原 AUTH-062、API-120）。理由是身份来源要唯一：两条入口意味着两套过期语义、两处吊销点，而其中一条（cookie）在界面上没有任何痕迹——升级时最容易被忘记的就是它，而它照样能换到一个 `admin` 身份。移除后 `identify` 只认令牌，`DELETE /session` 与 `oidc.json` 一并下线；退出登录即客户端忘掉令牌，服务端没有会话可销毁。恢复 OIDC 须重新分配需求号，不得复用已废弃的号。 | v0.1 |

## 兼容面的 access key 权限（实现期补充）

AUTH-002 写的是「access key 加 secret 加**策略绑定**」。前两项在 AUTH-072
至 AUTH-077 落地，绑定这一半此前没有做：`/api/aws` 只验签，签名对了就能建
设备、签证书、吊销、改策略、发布、写影子。一把只想让 CI 读设备列表的钥匙，
发出去的其实是 root。下面几条补上这一半。

| ID | 需求 | 状态 |
| --- | --- | --- |
| AUTH-081 | 每把控制面 access key 须带一个角色，取值与控制台的三个角色同名同义（AUTH-078）：`reader` 只读，`operator` 做日常写（建删设备、签发与吊销证书、改策略、发布、写影子），`admin` 另可动信任根（注册、改、删自有 CA，发凭证）。判定按级别高低比较，不逐条列举，否则总会漏掉某条路由上的 `admin`。角色取不到、或取到的不是这三个之一时一律拒绝：拼错的角色名必须是拒绝，不能退化成放行。未装配角色查询时同样拒绝一切——漏接线要失败，不能退化成「不判权限」，那等于这条需求没做而又看不出来。 | v0.1 |
| AUTH-082 | 每条兼容面路由须在挂载处显式写出它要求的最低角色，**不得按 HTTP 方法推断**。两个方向都会错：`ListAttachedPolicies`、`ListTargetsForPolicy`、`SearchIndex` 在 AWS 的 REST 映射里是 POST 而语义是读，按方法判会把只读调用方挡在外面；`GET /role-aliases/{n}/credentials` 的语义是发凭证，按方法判会把它放给 `reader`。级别按**语义**定而不是按当前实现定：后者今天只回 503（本节点不签发云临时凭证），级别仍取 `admin`，否则哪天真签发了没人会想起来要抬一级。 | v0.1 |
| AUTH-083 | 权限不足返回 403 `AccessDeniedException`，与验签失败的 401 `UnauthorizedException` 必须是两种错误。两者的修法完全不同：前者要换一把权限更高的钥匙，后者要查密钥与时钟。合成一种之后调用方只能靠猜。这不与 AUTH-075「密钥不存在与签名不对是同一个拒绝」冲突——那条防的是探测密钥是否存在，而走到权限判定时签名已经验过，告诉持有者自己是 `reader` 不多透露任何东西。 | v0.1 |
| AUTH-084 | 密钥文件里的设备钥匙是 `{"id","secret","thing"}`（AUTH-076，权限来自这台设备已附加的策略），出现 `role` 字段要在启动时报错并指出改法——那是控制面的钥匙填错了地方。缺字段、多字段都要指出是第几条。宽松接受的话，那把钥匙会静静加载成功，然后以一台不存在的设备的身份去找策略、找不到、拒绝 CONNECT，而报错里不会有一个字指向填错的那一行。**修订说明**：原文还规定了控制面钥匙在同一份文件里的形状（`{"id","secret","role"}`），那一半随 AUTH-086 作废——控制面的钥匙不再写在任何配置文件里。 | v0.1 |
| AUTH-085 | 设备密钥文件按 AUTH-076 留在节点本地、启动时读一次、不进元数据复制日志。由此带来的两条限制须写进示例配置：改动要重启才生效；集群下每个节点各有一份，只加在一个节点上的钥匙在别的节点上是 401。**修订说明**：原文把这两条限制加在全部 access key 上，控制面那一批已随 AUTH-086 去掉这两条限制。secret 存不了哈希这一条对两者都成立——SigV4 是 HMAC，服务端得有原文；控制面那批因此改为加密存放（AUTH-087），设备那份仍是文件，由文件权限保护。 | v0.1 |

## access key 的发放与存放（实现期补充）

AUTH-081 给控制面的 access key 定了角色，但钥匙本身仍是一份节点本地的
JSON：改完要重启，吊销不了，集群下每个节点各有一份——只加在 A 上的钥匙，
打到 B 的请求是 401。下面几条把它搬进复制层并补上发放入口。

| ID | 需求 | 状态 |
| --- | --- | --- |
| AUTH-086 | 控制面的 access key 须存进复制的元数据冷层，随同一条已提交日志复制（CLU-065），不再有 `aws_api.keys_file`。旧配置里还写着这一项时须在启动时拒绝并指出改法，不得静默忽略——忽略的后果是那份文件里的钥匙一把都不生效，而现象只是全部 401，没有一个字指向配置。它和角色别名、已注册 CA 同属「只进冷层、不进热视图」的一类：验签发生在控制面的 HTTP 请求上，不在连接路径上，读一次 KV 可以接受；热视图的位置留给每条消息都要查的那几样。 | v0.1 |
| AUTH-087 | **（AUTH-092 废弃）** secret 须加密后落盘。SigV4 是 HMAC，服务端必须拿到原文，所以它和证书私钥不同——存不了哈希，只能加密。封装用 PBKDF2-HMAC-SHA256 派生加 AES-256-GCM，头部（迭代次数与盐）进附加认证数据，access key id 也进附加认证数据：不绑 id 的话，把两条记录的密文对调就能让一把钥匙用上另一把的 secret，而两条记录本身都合法。盐跟着每条记录走而不是全局存一份：全局一份要先回答「谁来创建它」，两个节点同时写第一把钥匙会各生成一个盐，输家那条记录从此解不开。派生结果按盐缓存，新钥匙复用已有记录的盐，否则有多少把钥匙，进程启动后就要付多少次 60 万轮的派生。 | v0.1 |
| AUTH-088 | **（AUTH-092 废弃）** 加密用的口令就是 CA 那一个（`OPENIOTD_CA_PASSPHRASE` 或 `pki.passphrase_file`）。不另设一个：数据目录的静态保护本来就由它承担，两份秘密只会多一处配错的地方，而安全性并不提高——它们落在同一个数据目录里。启用 `aws_api` 时口令变成必填，没有就起不来；发钥匙时若取不到口令须明确失败，不得退化成明文存储。换口令之后已有的钥匙解不开，须重发。 | v0.1 |
| AUTH-089 | 每把钥匙带创建时刻、可选的到期时刻与停用开关。停用与删除都要有：怀疑泄露时要的是「立刻停掉并且留下痕迹」，而删除之后审计日志里的 `ak:AKIA…` 再也对不上人。停用、过期、不存在三者对调用方是同一个 401（AUTH-075），否则停用一把钥匙反而成了一个探测它是否存在的接口。id 形如 `AKIA` 加 16 个 base32 字符共 20 位，secret 为 40 个 base64 字符，与 AWS 一致——SDK 不校验形状，贴近真实只为省掉「这是不是填错了」这类提问。 | v0.1 |
| AUTH-092 | **静态加密整条移除，连同它要求的那个 CA 口令。** 废弃 AUTH-087 与 AUTH-088，并废弃环境变量 `OPENIOTD_CA_PASSPHRASE` 与 `pki.passphrase_file`（后者配了须在启动时拒绝并指出改法，理由同 AUTH-086：静默忽略会让运维以为私钥是加密的，而磁盘上那份是明文）。签发 CA 私钥以普通 PEM 落盘，access key 的 secret 以明文存进复制的冷层，保护只剩数据目录的 0700 与文件的 0600。**换到的是部署与运维的简单**：此前四种部署方式、五个验收脚本与 CI 的冒烟各要想一遍「同一个口令怎么送进容器」，k8s 还为它单设了一个 Secret，而送错一次的现象是节点起不来——这个代价落在每一次部署上，而加密只在「磁盘被拿走」这一种情形下起作用。**放弃的保护要写明，不得含糊**：数据目录或它的任何一份备份泄露，等于泄露整条信任链的签发能力与全部 access key，而那时吊销单张设备证书无济于事；access key 的处置是删掉重发。需要静态加密的部署在**卷那一层**解决（dm-crypt、云盘加密、k8s 的 etcd 静态加密与 PVC 加密），不要把口令加回应用层——`internal/pki` 的 `KeyStore` 接口仍留着 PKCS#11 与 KMS 两个后端的位置（CLU-030），那才是加强这一层的正确方向。门禁须把「明文」钉成显式事实而不是沉默的默认：原先那条「扫数据目录确认 secret 不以明文出现」反过来断言它**确实**在（TST-153）。 | v0.1 |


## 主体类别的边界（实现期补充）

角色名在三处同名（AUTH-078 的控制台角色、AUTH-081 的 access key 角色），
设备侧又另有一套策略判定（AUTH-002 起）。同名不等于同一套凭据，但文档此前
只在 UI-075 的界面描述里顺口提了一句。下面两条把边界定成需求：写错的后果
是给人发错凭据——以为 access key 能登控制台，或者以为给了控制台用户
`operator` 就等于 SDK 能写设备，而两种误解都要等到 401/403 才暴露。

| ID | 需求 | 状态 |
| --- | --- | --- |
| AUTH-090 | 控制面有两类互不相通的主体，须分开定义，任何一侧的凭据都不得在另一侧获得权限。**控制台用户**的凭据是管理面令牌，作用域是 `/api/admin/v1/*` 与挂在同一端口上的控制台，角色（AUTH-078）约束的是管理面操作权限；**控制面 access key** 的凭据是 id 加 secret，由 SDK 客户端（`boto3`、`aws` CLI 及等价物）以 SigV4 签名（AUTH-072 至 AUTH-077）调用兼容面 `/api/aws`，角色（AUTH-081）约束的是可调用的 action 集合。两类凭据各自签发（用户经 API-058 一侧，钥匙经 API-125 至 API-127）、各自停用、各自记审计操作者（`admin`/用户名 对 `ak:AKIA…`）。两边的角色取值同名同义只是级别语义的复用，不构成凭据互通：管理面令牌打到 `/api/aws` 是 401，access key 打到 `/api/admin/v1/*` 也是 401。 | v0.1 |
| AUTH-091 | 设备是第三类主体，不与上面两类混谈。它的凭据是客户端证书（或 AUTH-076 的设备 WebSocket 钥匙），授权不走角色而走已附加的 IoT Policy 逐条求值。因此设备钥匙的记录里没有 `role` 字段，出现即为填错（AUTH-084）；控制台的策略调试器只按策略判定、不提供主体类型选择（UI-068），因为能被策略判定的主体只有设备这一类。文档与界面文案提到主体时须指明是哪一类，不得用「用户」或「钥匙」笼统互指。 | v0.1 |
