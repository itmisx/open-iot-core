## 订阅额度的权威（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| QTA-106 | 两份订阅额度各问各的权威，不得共用一个判定：**全局订阅额度的权威是路由表**（它数的就是路由表里的订阅条数），**每连接额度的权威是会话**。占用与归还两侧都适用。此前占用侧两份都问会话，于是会话与路由表一旦不一致，同一条订阅就会多占一份全局额度而路由表只是就地替换——额度自此永久多出一份。 | v0.1 |
| QTA-107 | 会话恢复重放订阅时，须逐条按"路由表里是否已有"决定要不要占全局额度。常见情形是不占（持久会话断开期间订阅一直留在路由表里），但重启之后路由表是空的而会话在 bbolt 里——那时重放是真的往路由表里新加，必须占。此前一概不占，于是重启后每条恢复出来的订阅都在白拿一条路由表条目。 | v0.1 |
| QTA-108 | 全局订阅额度耗尽的后果是**整个节点不能再新增任何订阅**，且只能重启恢复。因此凡是改动订阅额度占用或归还的代码，都须同时有"额度计数等于路由表订阅数"的断言覆盖（见 TST-034）。 | v0.1 |

### 为什么这条不变量值得单独写下来

订阅额度的错误不会立刻出事：它每次只偏一份，要跑很久才到上限，而到上限
时的症状（"订阅突然全部失败"）与成因（几天前某条接管路径算错了一次）之间
看不出任何联系。能抓住它的只有"额度计数恒等于路由表订阅数"这条每一步
都检查的不变量——它把一个要几天才显形的泄漏变成立刻可见的数字不等。


## 配额的配置覆盖（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| QTA-109 | 全部配额须可经配置按**名字**覆盖（兑现 QTA-001）。配额表一直支持覆盖表，而装配处从来没有传过它，于是 `connections` 这类上限在实际部署里等同编译期常量——现象是「配置里根本没有这一项」，而默认的 50 万只是一个来自云厂商商业分层的数字，自建场景没有理由继承它。名字的权威是 `internal/quota` 的配额定义（`quota.LookupName`），配置侧只存 `map[string]int`：在 config 包里另抄一份名字映射就是第二个真相，加一项配额要改两处，而漏改不会报错。值的语义与配额定义一致（速率为每秒数量、计数为上限、大小为字节或层级），`0` 表示取消该项限制。 | v0.1 |
| QTA-110 | 未知配额名须在启动时拒绝，不得静默忽略。把 `connections` 写成 `connection` 的部署若被忽略就会以默认上限运行，而运维以为配的是另一个数——这个错误只在真打到上限那天显形，那时它看起来像一次容量故障，不像一行配置打错了字。错误须指向具体字段并列出可用名字（NFR-060、NFR-065）。多项未知时报字典序最小的那一个：map 的遍历顺序是随机的，同一份坏配置两次启动报不同的字段，会让人以为改掉一处又冒出一处。 | v0.1 |
