## 2. v0.1 的再切分（实现期修订）

原 v0.1 挂了 392 条需求，含完整控制台（RBAC 与双语）、约 40 个 AWS action、
Prometheus 与 OTel、SDK 对照套件。这是小团队 6–9 个月的量——**它违反了
本文自己的 RMAP-001 与 RMAP-002**。里程碑的作用是拒绝，而这一版没有拒绝
任何东西。

更要紧的结构性问题：十三个包质量都达标，但**没有一个入口能跑起来**。
没有可运行的二进制，就既收不到真实反馈，也无法验证这些包组合起来是否成立。

因此把 v0.1 切成两步，`cmd/openiotd` 提前到第一步的第一项。

| ID | 决定 |
| --- | --- |
| RMAP-005 | v0.1 切分为「可用内核」与「AWS 兼容面」两步。切分依据是**能否独立交付价值**，不是实现难度。 |
| RMAP-006 | 可用内核的第一项交付物是可运行的 `openiotd`，而非又一个库包。此前每一轮都在攒包，攒包的边际价值在递减。 |
| RMAP-007 | 兼容面后置的理由：兼容性是本项目的卖点，但其价值依赖于内核先被真实设备验证过。先做兼容面等于在未验证的内核上叠加冻结契约（NFR-072）。 |
| RMAP-008 | 两步各自须满足完整门禁，不得以"反正后面还要改"为由降低任一步的质量标准。 |

### 2.1 v0.1 可用内核

目标：**能跑真实设备、能签证书、能吊销、能看状态**。对自建与内网隔离场景已有价值。

| 域 | 内容 |
| --- | --- |
| 入口 | `openiotd`：YAML 配置加等价 flags、data dir 与 manifest、节点身份、`/healthz` 与 `/readyz`、优雅关闭 |
| 协议 | MQTT 3.1.1 与 5.0（已完成）|
| 传输 | 8883 mTLS、443 ALPN（已完成）|
| 安全 | X.509 认证、IoT Policy 含全部策略变量（已完成）|
| PKI | 内嵌 CA 签发、CSR 签发、证书状态机、吊销即时断连（已完成）|
| 平台 | 完整 Device Shadow（经典与命名）|

| 持久化 | bbolt 冷层（LANG-021 修订）、会话与保留消息落盘、重启恢复 |
| API | 最小 Admin API：设备、证书、策略、连接、节点 |
| 控制台 | 单页只读：总览、设备列表、实时连接、单设备时间线 |
| 事件 | 连接与订阅生命周期（已完成）、Prometheus |

## 5. v0.4 集群（目标 +4–6 个月）

按 03-cluster.md 第 11 节的 A 至 E 五个阶段交付。

| 阶段 | 内容 |
| --- | --- |
| A | 节点模式、data dir、manifest、node identity、readiness |
| B | meta Raft、快照、leader 转发、view apply。**此阶段完成才可宣称高可用** |
| C | shard layout、Shadow 与 retained 的 Raft、term epoch 围栏 |
| D | 消息 mesh、兴趣传播、批量、背压、跨节点共享订阅与排队 |
| E | 集群运维 API、drain、备份恢复、故障注入测试全绿 |

同期：控制台集群与节点监控、全局配额分摊、可选的 PostgreSQL 与 MySQL 外部元数据后端。
