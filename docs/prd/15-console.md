# 15 管理后台

## 1. 定位

目标不是"也有一个后台"，而是在几个具体位置明显超过 AWS 控制台。
超越机会分两类，须分清：AWS 结构上做不到的（托管服务不暴露节点与集群内部），
以及 AWS 做得确实差的（策略调试、断连归因、实时视图）。

### 1.1 AWS 控制台的实际短板

| 短板 | 说明 |
| --- | --- |
| 策略调试几乎不可能 | 连接被拒只得到泛化的授权失败，不指出未命中语句，不给出策略变量求值结果。IoT Core 用户的头号痛点。 |
| 断连原因须跳转日志服务 | 原因字符串晦涩且与控制台割裂。 |
| 没有实时视图 | 看不到在线连接列表、实时消息流、订阅分布。内置 MQTT 测试客户端功能很弱。 |
| 没有节点与集群视图 | 托管服务的本质限制。自建场景下恰恰是运维最需要的。 |
| Shadow 只展示原始 JSON | 无 desired/reported/delta 对照，无历史。 |
| 其他 | 导航层级深、批量操作弱、检索须单独开启、无深色模式。 |

## 空状态（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| UI-030 | 列表与流为空时不得只显示"暂无数据"。空面板与坏掉的面板在界面上无法区分，而用户的第一反应一定是后者。空状态须说清三件事：通道是通的、现在确实没有数据、怎么造出一条来。 | v0.1 |
| UI-031 | 事件流的空状态须给出一条可直接粘贴执行的命令。"连一台设备试试"而不给命令，等于把问题又推回给用户。 | v0.1 |
| UI-032 | 空状态须区分"真的没有数据"与"被筛选条件滤空了"。后者的处置办法完全不同（去掉筛选），混在一起说会让人去排查不存在的故障。 | v0.1 |
| UI-033 | 回填结束前显示加载中，而不是空状态。否则首屏会闪一下"没有活动"再被历史事件填满。 | v0.1 |

全部七个视图已落地（设备、证书、连接、策略、概览、事件流，以及概览里的
配额表与事件计数）。实现为共用的 `Empty` 组件（`web/console/src/ui.tsx`），
四个槽位对应四件事：标题说"空的是什么"，正文说"为什么此刻是空的、这不是
故障"，`cmd` 给一条可直接粘贴的命令，`action` 给就在眼前的按钮或去处。
带筛选的三页（设备、证书、连接）另走 `EmptyFiltered`——滤空的处置办法是
去掉筛选，与排查故障相反，共用一句话会把人引向不存在的故障。

各页的"怎么造出一条来"是按依赖顺序给的，而不是各说各的：策略在证书之前
（签发必须指定已存在的策略），证书在连接之前（mTLS 是唯一接入方式），
连接页则额外指向事件流与策略调试器——设备在重连却不出现，原因只会在
那两处。

门禁由 `TestConsoleEmptyStatesAreActionable` 钉住：它读 TSX 源码，检查每
个列表页引用了自己的空状态文案、带筛选的页面区分了滤空、文案中英齐备，
并禁止再出现一行通用的"没有数据"（该文案键已从词典里删除）。

| UI-051 | 两条签发路径须分开呈现（分段切换加各自的说明），不得用一个不起眼的开关切换。混在一个表单里会让用户在没意识到的情况下选中"让服务端拿着我的私钥"。 | 废弃 |
| UI-052 | 私钥面板须提供复制与下载，且在用户取走之前，关闭按钮的文案要明说"私钥将丢失"。私钥不可再次获取，一个普通的"关闭"按钮等于鼓励用户丢掉它。 | v0.1 |
| UI-053 | 服务端返回的 `hint` 须单独呈现，不拼进错误信息里。签发失败的提示往往比错误本身有用（例如 EC 曲线编码那一类，见 PKI-049）。 | v0.1 |
| UI-083 | 控制台的签发界面**只提供服务端生成密钥对**这一条路径（`/certificates/issue`），CSR 签发不进控制台。**废弃 UI-051**：它要求把两条路径分开呈现，而分开呈现的前提是两条都在控制台里能走完——CSR 那一条走不完。浏览器里没有办法生成并保管设备私钥（Web Crypto 导出的私钥仍要落到用户自己手上，等于把 KeyStore 搬进页面），所以表单只能承担"把 CSR 贴进来"这后一半；而用户为此先在命令行上 `openssl req` 过之后，接着 `openiotd cert issue` 比切回浏览器更短。半截的表单比没有更坏：它让人以为控制台能全程代办。CSR 路径仍由 PKI-011、PKI-105 保留在 API 与命令行上，端点与互指提示（PKI-106）都不变。`api.ts` 里的 `signCSR` 一并移除——留着它会被 TST-136 判为无人调用。 | v0.1 |
| UI-084 | 既然只剩这一条路径，服务端那道"非回环地址拒绝经明文 HTTP 回传私钥"（PKI-045）就成了控制台签发唯一的硬失败，其 403 提示须作为 hint 原样呈现（UI-053），并在表单的说明文案里**预先**写出两条出路：在节点上 `openiotd cert issue`，或经 API 的 `/certificates/sign-csr`。先写出来而不是等它报错，是因为这个失败只在非回环部署上出现——也就是除本机试用之外的全部部署，而提示文案里指向的 sign-csr 此刻已不在控制台内，用户照着找不到。 | v0.1 |
| UI-054 | 测试客户端在浏览器里解码 JSON、定长 CBOR，以及没有 schema 的 protobuf 线格式（只显示字段号）。录制与回放是本机的一份 JSON，最多 500 条；回放只铺回消息带，不重新发给 broker。不引入 CBOR、protobuf 或 MQTT 库。 | v0.1 |

## 使用教程（实现期补充）

控制台到这一步能把每件事**做**出来，但解释不了「从零开始该按什么顺序做」。
现状是：接入方式写在 `tests/aws-sdk`、`tests/device-sdk` 的脚本里，影子与
策略的规则写在两个抽屉里（UI-071、UI-072），而「先发 access key、再建设备、
再签证书、再附策略」这条主线一个字都没有。后果不是功能缺失而是**人卡在第
一步**：SDK 的 endpoint 要带 `/api/aws` 前缀这一条没写在任何界面上，漏掉
之后拿到的报错是 `invalid character '<'`（请求打到控制台首页，拿回一页
HTML），没有一个字指向真因。下面几条把教程定成产品的一部分，而不是仓库里
几份谁也不会去读的脚本。

内容源是一棵规范的多级目录 markdown，不是写进 TSX 的长字符串：教程会被
反复修订，而 TSX 里的长文无法 review diff，也不能脱离控制台单独阅读。
markdown 由前端自己解析（一个受限子集，一百多行），不引解析器依赖。
