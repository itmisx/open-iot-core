## 被拒连接的日志（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| OBS-100 | 被拒的连接须写入日志，字段含 clientId、thing、原因文案、原因码、来源地址、证书指纹与通用名、认证方式。凑齐这几项之后，多数接入问题不必再去翻别的地方。 | v0.1 |
| OBS-101 | 该日志由 `internal/server` 订阅连接事件后产出，而不是在 broker 里直接打。broker 的输出面只有事件总线（契约 11），它不该知道日志的存在。 | v0.1 |
| OBS-102 | 被拒日志须限速（当前每秒 10 条），被压制的条数与原因分布定期汇总上报。一个配置错误的设备会以秒级频率重连，每次都写一行会让它刷满日志，真正的问题反而被埋掉。 | v0.1 |
| OBS-103 | 成功的连接**不**写日志——量级太大，它属于指标。放行的授权判定同理。 | v0.1 |
| OBS-104 | 授权被拒同样须写入日志，字段含 clientId、thing、动作、资源、判定（ExplicitDeny/ImplicitDeny）、命中的策略与语句号、以及**策略变量的求值结果**。最后一项是关键线索：多数"策略看起来写对了却被拒"都是某个变量求出的值与预期不同（AUTH-035）。 | v0.1 |
| OBS-105 | 日志里的动作用策略文档的拼写（`iot:Subscribe`），不用事件内部的短名（`Subscribe`）。运维要能直接拿这个串去 grep 策略文件或贴进调试器——日志该说策略的词汇。 | v0.1 |
| OBS-106 | 连接拒绝与授权拒绝共用同一份限速预算，而不是各自一份。授权拒绝的量级可比连接拒绝高几个数量级（一个循环发布的设备），分开计数会让它把连接拒绝挤出日志。 | v0.1 |

### 由来

两次真实排障，同一个缺口的两层：设备连接返回 `NotAuthorized`、随后订阅
返回 `0x87`，两次服务端日志都一行都没有。原因只在事件总线上，而运维不会
先去订阅事件流，他会先看日志。

第二次尤其说明问题：第一层补完之后，缺口只是下移了一层。因此覆盖面要按
"设备可能被拒的全部环节"来定，而不是按碰到的那一个来补。

这与 AUTH-067 并不冲突：对**外**，"未登记"、"已吊销"、"策略不允许"共用
同一个原因码，使外部无法据此探测；对**内**，日志与事件把真实原因说清楚。
安全来自不对外区分，可运维性来自对内区分，两者在同一处实现。

## SSE 的命名事件（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| OBS-120 | 服务端给每条 SSE 事件写 `event: <Kind>`，客户端**必须**为每个类型 `addEventListener`。按 SSE 规范 `onmessage` 只接收类型为 `message` 的事件，即没有 `event` 字段的那些；只挂 `onmessage` 会一条都收不到。 | v0.1 |
| OBS-121 | 须有门禁测试把服务端的 `events.KindNames()` 与控制台的 `KINDS` 钉在一起。服务端加一种事件类型而控制台忘了加，后果是该类型被静默丢弃，而连接本身成功、状态灯仍显示"实时"。 | v0.1 |
| OBS-122 | `events.KindNames()` 是穷举事件类型的唯一入口，消费者不得各自维护会漂移的副本。 | v0.1 |

### 由来

控制台的事件流**从未显示过任何事件**。它只挂了 `es.onmessage`，而服务端
每条事件都带名字（`Conn`、`Authz`…），从不是 `message`。

这个故障的形态值得记下来：连接是成功建立的，状态灯显示"实时"，面板只是
空的。于是它看起来像"功能还没做"，而不是"坏了"——没有任何报错、没有任何
日志、没有任何测试失败。Go 端的测试断言 SSE 原文，那部分一直是对的；
缺的是把两端钉在一起的那一个断言，即 OBS-121。

"一个成功的连接 + 一个空面板"是最难发现的一类故障，因为它和"本来就没有
数据"在界面上完全一样。OBS-110 的回填与 UI-030 的空状态都是针对这一点：
前者让面板在有历史时不空，后者让它在真的没有数据时**说出来**。
