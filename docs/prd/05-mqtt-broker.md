### 由来

MQTT-063 只写了两种 DISCONNECT 的处置，实现就只实现了这两种：遗嘱仅在
MQTT 5 的 DISCONNECT reason 0x04 时发出，也就是**只在客户端主动请求发遗嘱
时才发**。设备掉电、断网、保活超时一律静悄悄——而那正是遗嘱存在的全部理由。

当时唯一的遗嘱测试恰好覆盖的就是能工作的那条路径，所以门禁一直是绿的。
缺口是真实设备对跑时发现的（`tests/device-sdk/`）。MQTT-064 把规范
（MQTT-3.1.2.5）里那条"除 DISCONNECT 外一律发出"写进基线，不再依赖
实现者自行补全。

MQTT-061 的延迟间隔是同一个缺口的另一半：属性解析了、存进会话状态了，
但没有任何地方读它，带延迟的遗嘱与不带延迟的一样立刻发出。MQTT-065 至
MQTT-067 把实现时必须定下的三件事写明——怎么与会话过期取舍、什么时候
取消、0x04 算不算——它们都是"不写下来就会各做各的"的那一类。

MQTT-068 是补 MQTT-064 时暴露出来的：遗嘱主题从来没有过授权判定。
在"只有客户端主动要求才发遗嘱"的旧行为下这个缺口够不着——要利用它，
攻击者得自己请求服务端代发，而那本就是它自己的连接。补上"掉线也发"
之后它才真正打开，所以两件事必须一起做。这也是一类值得记住的教训：
**把一条休眠的路径接通，会顺带把它上面所有未经审视的假设一起接通。**

## 保留消息的跨节点同步（实现期补充，2026-11-19）

起因是与 rmqtt 的对照：它的 retained 在集群里是通的，而本项目的能力表上
写着「没有」，且表现是**静默**——连到另一个节点的订阅者看起来像"这条
retained 不存在"。补法选了广播而不是共识，三个判据如下。

| ID | 需求 | 状态 |
| --- | --- | --- |
| MQTT-122 | 保留消息经 mesh 广播同步，**不进复制日志**。形状是「事件广播 + 新对端出现时全量 dump」：本节点写入或清除一条 retained 时把它广播给全部对端，收端按 MQTT-123 的判据合并。不进共识的理由是它在消息热路径上，而单组元数据写入的吞吐是每秒数千（见 `03-cluster.md`）；retained 也不需要线性一致。收到的远端更新**不再转发**（与 CLU-077 同理，否则两个节点之间无限弹）。 | v0.1 |
| MQTT-123 | 覆盖判据是 **Lamport 逻辑时钟**：`Version` 为 `(Counter, Node)`，按字典序比较，`Counter` 是本节点的单调计数器，`Node` 是节点 ID 的平手判据。收到远端更新时须把本地计数器抬到不低于对端（`Counter = max(本地, 远端)`，Lamport 的接收规则）。**不得用墙上时钟**（ARCH-033：各节点时钟不可比，用时间戳的后果是偶发的"旧消息覆盖新消息"，且极难排查），**也不得用 Raft 日志序号**（那要求 retained 进共识，MQTT-122 已经排除）。三条推论都要成立：同一节点同一毫秒连发两条，后一条必须赢（计数器单调，这是墙钟方案做不到而需要额外序号补的）；两节点并发写同一主题，**各节点收敛到同一个胜者**（字典序是确定性全序，这是"谁后到谁赢"做不到的，也是收敛不变量得以成立的前提）；重启后计数器由持久化的最大值抬起（`SeedVersion`，与 MQTT-109 同一个机制）。 | v0.1 |
| MQTT-124 | 清除保留消息须留**墓碑**（带 `Version` 的空负载记录），不得直接删除条目。直接删除时，一条迟到的旧负载会因为"本地没有记录所以不比版本"而被接受——现象是**已清除的保留消息自己回来了**。墓碑按 TTL 回收，TTL 须远大于一次 dump 周期。单机下这个缺陷碰不到（本地版本单调且不会迟到），所以它此前不是缺陷而现在是。 | v0.1 |
| MQTT-125 | 跨节点一致性的两条边界须写进部署文档，不得写成"一致"。其一，**生效窗口不是零**：A 写入后 B 上的新订阅者若在广播到达前订阅，收到的是旧值或空；要零窗口只有两条路（进共识、或在 SUBSCRIBE 路径上按需扇出拉取），都不在本阶段。其二，**稳态下丢一条广播没有自愈**：发送队列满或发送失败且该主题此后不再发布时，那个节点会一直缺这一条，且无人发现——补法是按主题前缀分桶的 digest 对账，属于下一阶段。 | v0.1 |
| MQTT-126 | 每个节点都保存**全量** retained，因此容量要按节点数乘：`topic.Limits` 的上限是本地的，三节点就是三份内存，广播还与消息帧共用同一条 TLS 连接。本阶段至少要有「retained 条数」与「广播丢弃数」两个指标；完整的容量项随 digest 对账一并补。 | v0.1 |
| MQTT-127 | 离线队列满（QTA-111）时**丢新到的那条**，不得挤掉最旧的。这样设备重连后收到的是已发布序列的一个**前缀**，顺序不被打乱；挤掉最旧的那种做法会让「收到了第 1、3、4 条」这类空洞出现，而 QoS 1 的使用者通常按顺序处理，空洞比缺尾更难发现。丢弃不得静默：由 `quota_rejected_total{quota="queued_messages_per_session"}` 暴露。发布本身不因此失败——发布者没有理由因为某个订阅者的队列满了而被拒。 | v0.1 |

## 接管的会话权威（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| MQTT-105 | 会话在本节点在线期间，**运行时是权威，存储不是**。接管同 clientId 的本地连接时，新连接须接过被抢占连接内存中的订阅集，不得回存储读。订阅与退订只改内存、落盘发生在断开时，而被抢占的连接因为索引已指向新连接而不会再落盘——回存储读到的是上一次断开时的快照。 | v0.1 |
| MQTT-106 | 接管不得重放存储中的离线队列。存储里那一份是被抢占的连接在本次连接开始时保存的，它随后已经 `flushQueued` 下发过且不再落盘，重放等于把投递过的消息再投一遍。 | v0.1 |
| MQTT-107 | 不再续上任何会话时（clean start，或存储中的会话已过期），路由表里该 clientId 的残留订阅须连同其占用的全局额度一起清掉。会话过期此前只是让恢复落空，没有人摘路由表，于是**新会话会收到自己从未订阅过的主题**——这不只是记账问题。 | v0.1 |

### 为什么权威必须明确到"哪一份状态说话"

MQTT-105 至 MQTT-107 是同一个缺陷的三个面：同一份逻辑状态（这个会话持有
哪些订阅）同时存在于三处——会话运行时、会话存储、路由表——而没有一处被
指定为权威。于是每条路径各自挑了一个顺手的来读，接管、过期、重启各挑了
不同的那个。

症状最先是以记账不符出现的（全局订阅额度与路由表订阅数不等，见 QTA-106），
但记账只是**可观测的那一面**。真正的后果是设备的订阅状态被悄悄改写：
退订之后又开始收消息，或者刚订阅的主题收不到。确定性模拟之所以能抓到它，
正是因为它每一步都在查那条记账不变量——不变量的价值在于把"看不见的状态
错误"翻译成"立刻可见的数字不等"。

替代方案是"每次订阅都落盘"，让存储始终是权威。它被否决：那会把一次写放大
加到订阅热路径上，而接管是罕见路径——代价放错了地方。

## 会话落盘与写出池的容量修正（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| MQTT-118 | 会话落盘（`Save` 与 `Delete`）走**合并提交**，不逐条 fsync。持久性不变：bbolt 的 `Batch` 仍在返回前提交并 fsync，只是把并发调用合进同一个事务——这与 MQTT-104 给保留消息开的口子不同，那里允许丢，这里不允许，所以也不能改成全局 NoSync（那才是真有丢失窗口的那一种）。改成合并的理由是这条写入在 **CONNECT 路径上**：逐条 fsync 时它就是建连速率的天花板，实测（darwin/arm64、Apple SSD）逐条 `Update` 串行 191 次/秒、512 并发 328 次/秒，而 `Batch` 在 512 并发下是 27268 次/秒。NFR-033 要求重启后 30 秒内恢复接受连接，而百万设备的重连风暴在逐条 fsync 下不可能收敛。代价是单条写入的延迟从一次 fsync 变成最多一个 `MaxBatchDelay`（bbolt 默认 10 ms），只有一个设备在连时它多等那 10 ms。约束：`Batch` 在重试时会**再次调用**事务体，因此事务体必须幂等，围栏判定（读当前 epoch 再比较）必须留在事务之外、由 per-clientId 的 lane 锁保护。 | v0.1 |

| MQTT-120 | 写出池的就绪队列**不得丢弃唤醒**。队列此前是容量 1024 的通道，满了就退回入队标记、等「下一次入队重试」——而被退回的那次唤醒没有任何人重试：连接出站队列里的字节要等它下一次有报文才被刷出去，没有下一次就一直压着。1024 这个容量在百万连接的扇出峰值下是常态饱和，所以表现不是偶发延迟而是大面积投递停滞，而单机小规模的用例一条也压不到（实测 3000 条连接、2 个工作协程时只有 1439 条被刷出）。改为侵入式链表：入队标记已把队列长度约束在连接数以内、每项一个指针，所以它可以无界——无界换来的正是「唤醒不会丢」。它同时消掉了老实现用 `close(队列)` 停工的那道缝：判定与入队现在在同一个临界区内，与 ARCH-074 对出站队列的要求是同一条理由。 | v0.1 |
| MQTT-121 | 接入层的运行参数（TLS 握手并发上限、写出池协程数、每连接出站队列深度、读缓冲初始大小、单次写出合并上限、刷写超时、TCP 内核保活周期）须可配，零值表示取默认值。默认值只在 `internal/broker` 存一份，配置层不复制：抄过来就是第二个真相，而两处数字不一致时没有任何测试会发现。校验只拦「填了会让节点自毁」的取值（例如 1 ms 的刷写超时会把每个客户端都判成慢客户端并断开，而现象是「所有设备都连不上」，不指向那一行配置），不替使用者判断合理区间。 | v0.1 |
