## 1. 定位

语义须逐字段对齐，是 SDK 对照测试的重点区域。
分区单写者（契约 06）加 Raft log index 派生版本号（CLU-007）使并发正确性无需额外设计。

### 3.1 SHDW-026 的修订（实现期）

原文写的是"`version` 由分区 Raft log index 派生"。实现时发现它与两件事直接冲突：

- **与 SHDW-028 冲突**。删除后重建须从 1 开始，而 log index 只增不回退。
- **与 AWS 语义冲突**。AWS 的 version 从 1 开始、每次更新加一，是一个小整数；
  log index 会跳号（其他影子、其他命令都占用索引），设备侧做乐观并发时
  拿到的版本会出现无法解释的跳跃。

CLU-007 的本意是对的，只是表述取了错的落点：**需要 Raft 保证的是"顺序确定"，
不是"版本值等于索引"**。修订后的表述把两者分开：版本是复制状态的一部分，
它的递增发生在确定性的 apply 中，因此跨 leader 变更安全；而决定 apply 顺序的
是日志索引。被禁止的仍然是进程内计数器与时间戳——前者在 leader 切换后会回退，
后者在时钟回拨时会回退。

| ID | 需求 | 状态 |
| --- | --- | --- |
| SHDW-029 | 变更命令须携带时间戳，apply 时不得读时钟。各副本若在 apply 时各读一次墙上时钟，会算出不同的 metadata 时间戳，状态机不再确定，日志重放与快照的结果也不再一致。这是契约 08 在复制状态机下的具体含义。 | v0.1 |

## 3.2 合并规则（实现期确认）

SHDW-021 标注"最容易做错"。实现时把规则逐条固化，每条都有对应测试：

| 序号 | 规则 |
| --- | --- |
| 1 | 更新是深度合并，不是整体替换。 |
| 2 | 显式 `null` 删除该键**及其元数据**，任意深度。 |
| 3 | 被 `null` 删空的**嵌套**对象保留为 `{}`，其元数据同为 `{}`。 |
| 4 | 但**顶层** `desired`/`reported` 段若为空则整段不保留。 |
| 5 | 数组整体替换，不逐元素合并；其元数据是逐元素的时间戳数组。 |
| 6 | 出现在更新中的每个叶子都获得本次更新的时间戳，即使值未变化；`update/accepted` 的元数据含 `null` 叶子，而已存储文档中它们已被删除。 |

规则 3 与规则 4 的不对称是真实行为，不是笔误：嵌套的空对象是用户数据的一部分
（"这个子对象存在但没有字段"是有意义的状态），而空的顶层段只是"没有这个段"
的另一种写法。

| ID | 需求 | 状态 |
| --- | --- | --- |
| SHDW-022a | 元数据树必须由**状态树**驱动，不得依据元数据自身的类型判断结构。标量的元数据 `{"timestamp": N}` 与对象的元数据在宿主语言中同为映射类型，据类型复用会在"标量被对象替换"时产出既非叶子亦非镜像的畸形元数据。此处已有实测缺陷与回归测试。 | v0.1 |
| SHDW-022b | 须有"元数据镜像状态"的不变量断言，并由随机操作序列与 fuzz 持续验证。畸形元数据不会让任何操作报错，它只是对设备撒谎——因此只能由不变量来守，不能靠逐个用例。 | v0.1 |
| SHDW-023a | `state` 下的未知段（如把 `reported` 拼成 `report`）须报错而非忽略。静默接受会让设备以为上报成功而影子毫无变化，这种故障没有任何可观测症状。 | v0.1 |
| SHDW-026a | 数字按字面量保留与比较（`1` 与 `1.0` 视为不同）。解析为浮点会让 `1.50` 变成 `1.5`、大整数丢精度，而影子是设备与云之间逐字段比对的契约。 | v0.1 |
| SHDW-021a | **待与 AWS 对照验证**：数组元数据在"更新设置了一个与原数组等长的新数组"时，AWS 文档提到可能保留原有逐元素时间戳。本实现采用更简单的规则——被更新设置的数组，每个元素都取本次更新的时间戳。差异须由 SDK 对照测试确认后再定。 | 待验证 |
