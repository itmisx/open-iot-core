### 关闭顺序（NFR-065a）的由来

实现 `internal/server` 期间，这段顺序上踩了两个坑，**两次直觉顺序都恰好是错的**，
且两者在生产日志里的表现都只是"关闭慢"或"进程没了"：

| 错误写法 | 症状 | 原因 |
| --- | --- | --- |
| 先 `Listener.Close()` 再 `Broker.Close()` | 永久死锁 | `Listener.Close` 要等连接处理协程，而那些协程正阻塞在读客户端套接字上，只有 `Broker.Close` 能放开它们。因此监听器须拆出只停止接受的 `StopAccepting` |
| 管理端点在 `wg.Wait()` 之后才关 | 每次关闭恰好耗满 30 秒超时 | 管理端点的 `Serve` 协程登记在同一个 `WaitGroup` 上，等待排在叫停之前 |

两者都只因为装配逻辑放在了可测的包里、并且真的断言了关闭耗时才被发现——
在 `cmd` 包里它们都会被"进程随即退出"掩盖。这条经验推广为 TST-100。
| NFR-065 | 关键故障须有可操作的错误信息：说明发生了什么、影响范围、如何恢复。 | v0.1 |

## 部署与分发（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| NFR-100 | 容器镜像由打 tag 触发的流水线构建并推送到 `ghcr.io/<仓库>`，覆盖 linux/amd64 与 linux/arm64。发布前先过一遍完整门禁：tag 可能打在任意提交上，发一个没过门禁的版本比晚发几分钟糟得多。标签为 `{版本}`、`{主}.{次}` 与 `latest`，带后缀的预发布不动 `latest`——否则 `:latest` 会在某一天悄悄变成预发布版本。推送后须跑一次冒烟（init、serve、`/readyz`）：镜像推完了才发现它起不来是最难堪的一种发布。 | v0.1 |
| NFR-101 | 镜像以非 root 运行，数据目录是卷，不设默认 `serve` 之外的自动初始化。`init` 与 `serve` 分两步（CLU-055）在容器里同样成立：编排侧用一次性服务或 initContainer 承担 init，而不是让 serve 自动建目录。**后半句经 NFR-105 修订**：单节点 compose 改用镜像入口的 `OPENIOTD_AUTO_INIT`，与一次性服务等价（两者都是编排在初始化，`serve` 的脾气不变）；集群两份仍用一次性服务与 initContainer，因为那一步还要分发设备 CA。 | v0.1 |
| NFR-102 | 仓库须给出单机 Docker、三节点 compose 与三节点 Kubernetes 三份部署清单，并逐份说明它提供与**不提供**什么。集群清单须写明：多数派是 `成员数/2+1`，扩到偶数不提高容错；跨节点互斥是最终一致；跨节点共享订阅组尚未支持。没有这段的部署文档会让人按「高可用」去用一个并非如此的配置。 | v0.1 |
| NFR-103 | 集群部署中三个节点必须共用同一套设备 CA：设备证书由任一节点签发，而设备可能连到任意节点——各节点自备 CA 时，一台设备只能连上签发它的那个，其余节点 mTLS 直接握手失败。复制链是与设备 CA 无关的另一条信任链（CLU-068），每张节点证书的 CommonName 必须等于节点 ID。 | v0.1 |
| NFR-104 | 数据目录的位置须对**所有**子命令一致地由 `OPENIOTD_DATA_DIR` 决定。实测犯过的错：`cert issue` 无条件把 flag 默认值传下去（命令行优先级高于环境变量，于是环境变量永远被盖住），`admin token` 根本不走配置解析。容器里数据目录正是靠环境变量指向卷的，两者的表现是要么因无权限而失败，要么在别处**另建一套 CA**——签出来的证书连不上正在跑的节点，而两边都不报错。 | v0.1 |
| NFR-105 | 容器入口须给「serve 之前补一次 `init --if-needed`」留一个**默认关闭**的开关（环境变量 `OPENIOTD_AUTO_INIT`），使单节点的快速开始收成一条命令。这不放宽 NFR-101 与 CLU-055：`serve` 本身的脾气不变，自动初始化只存在于镜像入口这一层，且必须显式打开。开关只对 `serve` 子命令生效——一条 `config print` 不该顺手建出一个数据目录；只认 `1` 与 `true`，因为「非空即为真」会把 `OPENIOTD_AUTO_INIT=0` 读成打开。代价须在文档里写明并且只由开它的人承担：**打开它之后卷挂错路径不再报错**，而是静默初始化出一个空节点，于是原有设备全部认证失败——正是 CLU-055 要防的那个症状。**集群的两份清单不得设它**（NFR-103）：那里它会让每个节点各建一套设备 CA，而集群的 init 还要把第一个节点的设备 CA 分发给其余节点，这一步必须单列。单节点的 compose 清单**可以**设——这一处修订 NFR-101 的措辞：一个**无条件执行 `init --if-needed` 的前置服务**与这个开关在「卷是空的就静默初始化」这一点上完全等价，两者都是编排在初始化，所以那份清单从两个服务收成一个并没有放宽任何约束。真正的分界是谁掌握数据卷：清单里卷与服务写在同一份文件里，而裸 `docker run` 的 `-v` 由敲命令的人现写，所以那条路径上生产仍用两步。它是镜像层的变量而非配置键，`openiotd config env` 列不出它。 | v0.1 |
