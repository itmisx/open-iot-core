## 文件化注册表（v0.1 内核阶段的临时实现）

元数据的权威来源是 Raft 日志加 bbolt 冷层（契约 05、06）。在冷层落地之前，
v0.1 内核阶段用 data dir 下的 JSON 文件代替，目的只有一个：让二进制现在就能跑通
「签证书、绑策略、设备接入、吊销」的完整链路。没有它，`serve` 启动起来是一个
拒绝所有设备的空 broker，无法验证任何东西。

| ID | 需求 | 状态 |
| --- | --- | --- |
| REG-100 | 文件化注册表的读写只经 `meta.Store` 的命令接口，与将来的 Raft 实现走同一条路径，使替换后端时上层无需改动。 | v0.1 |
| REG-101 | 注册表文件须带 `format_version`，未知字段一律报错。 | v0.1 |
| REG-102 | 策略集编号由策略文件名排序决定，因此跨重启稳定。见 TST-106。 | v0.1 |
| REG-103 | 语法错误的策略须使启动失败。带着一份编译不过的策略继续运行，等于把该策略下的所有设备静默降权或提权。 | v0.1 |

## 控制面（internal/registry）

控制面是冷层（完整记录）与热视图（鉴权路径读取的子集）之间的**唯一写入口**。

| ID | 需求 | 状态 |
| --- | --- | --- |
| REG-110 | 冷层与热视图须在同一次调用里一起更新。两者分开写会留出一个窗口——冷层说"已吊销"而热视图还放行——那正是吊销失效的样子。 | v0.1 |
| REG-111 | 更新顺序为**先热视图、后冷层**。反过来的窗口是不安全的；先改热视图则最坏情况只是冷层落后（展示上暂时不一致），而安全判定已经生效。 | v0.1 |
| REG-112 | 策略集编号须跨重启稳定、单调，且不得重用已删除策略的编号。编号被证书与设备记录引用，重用会让旧引用指向新策略——设备拿到别人的权限，而日志里什么异常都看不到。实现用持久计数器而非"记录条数加一"。 | v0.1 |
| REG-113 | 删除证书登记之前须先将其置为 `REVOKED` 并触发断连。仅删除登记不会产生"变为不可连接"的转换，在用连接会一直留着直到自行断开——那等于一次未完成的吊销。 | v0.1 |
| REG-114 | 绑定不存在的策略或设备须在写入时拒绝。放过它会让设备在下次连接时被拒，而错误信息指向设备而不是指向这次错误的绑定。 | v0.1 |
| REG-115 | 未知的证书状态字符串须映射为**不可连接**。映射为可连接会让一个拼错的状态值变成放行。 | v0.1 |
| REG-116 | 热视图只物化策略真正引用的属性。属性槽位由编译期收集的 `CompiledSet.AttrRefs()` 给出；槽位变更后须重写全部设备的投影——投影按槽位下标，顺序一变旧投影就指向了别的属性名，策略会读到错的值。 | v0.1 |
| REG-117 | 列举接口只提供分页入口，不提供"返回全部"。百万设备下后者是一次把整个冷层读进内存的操作，而调用方多半只要展示一页（REG-044）。 | v0.1 |
| REG-118 | 启动时恢复的顺序为策略、设备、证书。证书与设备按策略名绑定，策略尚未登记时绑定会落空，而落空的表现是"设备连不上"。 | v0.1 |

### 文件化注册表的归宿

`openiotd init` 写出的示例策略与 `cert issue` 登记的证书仍经文件化注册表产生，
启动时**一次性导入**控制面，之后由控制面接管。导入是幂等的，重复启动不会重复创建；
证书绑定的设备在文件格式里是隐含的，导入时补建为显式设备记录。

## 控制面的重建必须先于任何写入（实现期补充）

| ID | 需求 | 状态 |
| --- | --- | --- |
| REG-119 | 启动时**先**用冷层重建热视图，**再**导入文件化注册表。顺序反了的后果是节点起不来，而报错指向策略而不指向顺序：写入前的校验要求绑定的策略同时在冷层（给编号）与热视图（给编译结果）里，少一层就拒绝（REG-110、REG-111 的同一处判定）。第一次启动时冷层是空的，策略由导入自己写进去、两层一起写，所以那一次反着也能过；而第二次启动时冷层已经有策略、导入会跳过它，热视图却要等重建才有——于是「serve 过一次、再 `cert issue`、再重启」这条路以「策略不存在」失败，而那份策略明明在冷层里。这与 CLU-072 是同一类：一份逻辑状态摊在两层上，而校验读的是两层的**交集**，因此重建必须发生在任何写入之前。导入之后的记录不在重建时的统计里，启动日志的条数须补数一次，且只在真导入了东西时补——常规启动不该为几个数字多扫一遍整个冷层。 | v0.1 |

### 由来

这条是部署清单重做时实测撞到的：按文档走完单机容器的流程（`init` →
`serve` → `cert issue` → 重启），节点进入崩溃重启循环。`cert issue` 自己的
提示写的就是「需重启才会载入新证书」，所以这条路是既定用法而不是误用。

值得记下来的是**为什么测试没抓住**：既有的幂等性测试（TST-111）在第一次
启动**之前**就把证书签好了，于是导入发生在一个空冷层上，策略由导入自己写
进两层——那一次顺序反着也能过。缺的是「签在第一次启动之后」这一个顺序，
而两条路径在代码里走的是同一个函数。
