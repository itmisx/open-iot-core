# 基线数据

两份东西放在这个目录下，用途不同：

- `memory.json` 是**门禁比对的对象**（本页下半部分），改大要给理由。
- `throughput.md` 与 `throughput/` 是**端到端基准的公开结果**（TST-060、
  TST-163），不进门禁——耗时随机器变化，写进门禁等于让一次 CI 的机器调度
  决定合并与否。它由 `make bench-e2e` 产出，原始数据与环境记录一并入库。

## 内存基线（TST-127、CLU-021）

这三个数字是门禁比对的对象：实测高于记录的 110%（或低于一半）即失败。
耗时**不在**这里——它随机器、负载与竞态检测器变化，写进基线就是发布
无法复现的数字（TST-127 的刻意决定）。

| 键 | 含义 | 记录值 | 来源用例 |
| --- | --- | --- | --- |
| `hotViewBytesPerDevice` | 百万设备热视图里每台设备占的字节 | 188 | `internal/meta` 的 `TestViewMemoryBudget` |
| `trieBytesPerSubscription` | 百万订阅的订阅树里每条订阅占的字节 | 185 | `internal/router` 的 `TestTrieBytesPerSubscriptionBaseline` |
| `connBytes` | 一条已完成 CONNECT 的空闲连接在堆上的字节 | 934 | `internal/broker` 的 `TestConnMemoryBudget` |

**原始记录于 2026-10-31，连接基线更新于 2026-11-22**，darwin/arm64、
go1.24.4。这三个数都是对应用例在本机
实测打印出来的值——此前仓库里没有这份文件，于是那三条用例一直以
「读不到基线」失败，而失败信息里正好印着该记的数。
连接基线先从 13096 降到 5416：初始读缓冲从 4 KiB 降到 1 KiB，编码与
写出缓冲改为首次使用时按需分配；本轮再用读缓冲 1 KiB→256 B 与默认出站
通道 64→32 降到 3368；认证输入与运行期连接字段拆分后进一步降到 3112；
出站队列改为一个内联槽、第二条积压才分配完整环形缓冲后降到 1688；证书
Subject/Issuer 的常见 DN 字段内联、稀有字段按需分配后进一步降到 1560。
CONNECT 分段耗时从长连接主对象移到结果事件发出即回收的 sidecar 后进一步
降到 1430--1431；主对象由 1024 B 分配档进入 896 B 档。
空出站队列的首槽、ring 与游标再移到按需 sidecar，完全排空即回收，基线进一步
降到 1350--1351；CLU-179 再把证书策略上下文改为按需侧挂并消除
`Principal` 的对齐洞，降到 1222--1223。
CLU-180 将 CONNECT 后不再需要的握手耗时移入 sidecar、标准 ALPN 紧凑编码，
并把 WSS 专用字段按需侧挂后进一步降到 1158--1159；CLU-182 消除重复 Thing、
无收益编码 slice 和逐连接配置后降到 1095；CLU-184 再把多帧 writer 缓冲与
QoS 重试状态按需侧挂、紧凑保存远端地址和 keepalive，降到 1030--1031；
CLU-185 把仍可一次容纳常见控制报文的内联读缓冲调到 192 B，降到约 966；
CLU-186 把合并缓冲改为 writer 池借还并压缩游标/状态位，降到约 934。

`connBytes` 只量连接对象与 Runtime，不含 Broker 的全局索引。证书索引另以
20 万唯一 mTLS 指纹做容量基准（CLU-155）：单元素嵌套 map 改为内联 owner 后，
由约 50.99 MB / 400,513 allocs 降到 14.69 MB / 513 allocs，按 20 万连接约少
34.6 MiB/节点。最终容量判断仍以 Linux 密度轮的进程 RSS 为准。

改大这些数字要说明结构上为什么变大。低于一半同样失败：那通常是对象被
回收了、测量没有量到该量的结构，而不是优化成功。
