原则 01

集群是接口，单机是实现

所有跨节点关注点在 v0.1 就以接口形式落地，单机实现填充它。单机版不是"集群之前的版本"， 而是"节点数为 1 的集群"。两者共用同一条代码路径。

原则 02

连接路径不许有网络调用

认证、鉴权、配额判定全部查本节点内存中的物化视图。元数据通过复制日志更新视图， 而不是让 CONNECT 去远端查库。这条决定了握手吞吐的上限。

原则 03

声明式取代回调

策略、注册模板、规则都在进程内求值，不走 webhook / Lambda。 逃生口是 WASM 插件（进程内沙箱），而不是网络回调。

PART I

集群优先的架构契约

broker 的集群化之所以几乎总是演变成重写，原因不在共识算法难，而在于单机实现会把 "本地"这个假设焊进会话结构、路由签名和认证路径。下面四个平面与十二条接口契约， 是为了让 v0.4 填的是实现而不是重构。

四个平面，四种一致性

把它们混成一个"集群模块"是第二个常见错误。四者的写入频率、一致性要求和失败后果完全不同， 必须分开选型。

元数据平面strong · 低写入
内容 Thing / Thing Group / 证书与状态 / 策略 / 注册模板 / Job 定义 / 规则 实现 复制日志（Raft）+ 每节点全量内存物化视图。读永不走网络。 失败后果 写不可用（可接受）；读仍可用（视图略滞后）。
会话与路由平面fenced · 中写入
内容 clientId→节点归属、订阅兴趣、共享订阅组成员 实现 归属用带 epoch 的租约；兴趣用 gossip 摘要（最终一致）。 失败后果 短暂重复投递或漏投；绝不允许同一 clientId 双活。
消息平面none · 高吞吐
内容 节点间 PUBLISH 转发 实现 自有 mesh（长连接 + 批量 + 背压），不经共识。 失败后果 QoS 0 丢，QoS 1 由发送侧重试。
持久队列平面durable · 可插拔
内容 离线 QoS 1 队列、retained、共享订阅积压 实现 可插拔。默认 pinned-to-node（节点故障丢失，明确声明）；可选复制后端。 失败后果 取决于后端。不要在 v1.0 承诺跨节点零丢失。
PART I · 契约

十二条 Day-1 接口契约

每条都给出：接口形态、单机实现、集群实现、以及 延后到 v0.4 才做会付的重构代价。 判据很简单——凡是会改变函数签名或数据结构形状的，必须现在做；凡是只换实现体的，可以延后。

01

会话归属与抢占围栏

DAY-1

MQTT 要求同 clientId 后连接踢掉前连接。单机下这是一个 map 操作；集群下这是分布式互斥， 且必须防止网络分区造成双活。Epoch 是唯一的解法，而它必须贯穿整个会话层。

// Epoch 对每个 clientID 单调递增，跨节点全局有效。
type Epoch uint64

type SessionOwnership interface {
    // Claim 抢占所有权并返回新 epoch。若当前由他节点持有，
    // 实现必须保证旧持有者会收到 Eviction（无论是主动通知还是租约过期）。
    Claim(ctx context.Context, clientID string, node NodeID) (Epoch, error)
    Release(ctx context.Context, clientID string, e Epoch) error
    Lookup(ctx context.Context, clientID string) (NodeID, Epoch, bool)
    Evictions() <-chan Eviction
}

// 所有改变会话状态的操作都必须带 epoch 并校验，包括本地操作。
func (s *SessionRuntime) Deliver(e Epoch, m *Message) error // epoch 不匹配 → ErrStaleEpoch
单机实现
内存 map + 本地原子计数器。Evictions() 走进程内 channel。
集群实现
按 clientID 哈希分片的租约（Raft 组或分片 leader）。epoch = 分片内单调序号。
延后代价

会话层所有方法签名都要加 epoch 参数，调用点遍布协议状态机、投递路径、持久化。 实测这是会话模块的全量重写。epoch 字段的成本现在是零，事后是整个模块。

02

路由返回本地与远端两份目标

DAY-1

这是最廉价也最关键的一条。单机 broker 几乎都写成 Route(topic) []*Session， 于是投递路径直接拿到了会话对象。集群化时必须在中间插入"序列化 + 转发"， 而整条路径已经假设了目标是本地指针。

// 从 v0.1 起就是两份返回值。单机下 remote 恒为 nil。
type Router interface {
    Subscribe(sub Subscription) error
    Unsubscribe(clientID, filter string) error
    Route(topic string) (local []SubRef, remote []NodeID)
    // 共享订阅单独走，因为选一个订阅者的逻辑是全局的
    RouteShared(topic string) (groups []SharedGroupTarget)
}

// 投递器从 v0.1 就有两条分支。
func (d *Dispatcher) Publish(m *Message) {
    local, remote := d.router.Route(m.Topic)
    d.deliverLocal(local, m)
    if len(remote) > 0 { d.transport.Forward(remote, m) } // 单机永不进入
}
单机实现
本地订阅树；remote 恒 nil；Transport 为 loopback 空实现。
集群实现
本地树 + 远端兴趣集（契约 03）；remote 去重后批量转发。
延后代价

投递路径、retained 下发、LWT、共享订阅、Shadow/Jobs 回包全部要改。 而且这些路径上通常已经写了"拿到 session 就直接写它的 writeCh"，改动会牵出并发模型。

03

主题分类：设备域 vs 通配符域

DAY-1

IoT 场景的结构性简化，是本项目相对通用 broker 的最大性能杠杆：设备只订阅自己的主题 （$aws/things/{自己}/shadow/...），只有后端应用订阅通配符，而后端连接数是几十不是几百万。 因此设备域主题的路由可以纯靠哈希算出，完全不需要进入全局订阅表——只有通配符订阅需要全局复制。

type TopicClass uint8
const (
    // $aws/things/{thing}/... —— 归属节点可由 thingName 直接算出，
    // 不占用全局订阅表。这是百万级 filter 下唯一可扩展的做法。
    ClassDeviceScoped TopicClass = iota
    // 保留主题中只可能被精确订阅命中的
    ClassReservedExact
    // 普通业务主题，需要兴趣传播
    ClassGeneral
)

func Classify(topic string) (TopicClass, ScopeKey)  // ScopeKey = thingName

EMQX 的做法是把整棵订阅树全局复制（Mnesia），在百万级不同 filter 下会崩。 我们从一开始就不付这个代价。

单机实现
分类函数照常调用，结果用于选择本地子树，顺带获得更好的缓存局部性。
集群实现
设备域 → Partitioner.Owner(thingName)；通用域 → 兴趣集匹配。
延后代价

不致命，但事后补会发现订阅树已经按"一视同仁"组织，要重建索引结构与兴趣摘要格式。 更麻烦的是届时已有的性能基线会倒退，难以说明原因。

04

会话状态与会话运行时分离

DAY-1

本清单里事后代价最高的一条。绝大多数单机 broker 把 net.Conn、 chan、sync.Mutex 直接塞进 session 结构体。一旦如此， 持久会话落盘、会话迁移、跨节点接管、控制台的会话快照——全部无从下手。

// 纯数据。可序列化、可复制、可跨节点搬运。
// 禁止出现：net.Conn / chan / func / sync.* / unsafe.Pointer
type SessionState struct {
    ClientID       string
    Epoch          Epoch
    Owner          NodeID
    ProtoVer       byte          // 4 = 3.1.1, 5 = 5.0
    ExpiryInterval uint32
    Subscriptions  []Subscription
    Inflight       []InflightMsg // 出站未确认 QoS1
    Queued         []QueuedMsg   // 离线队列
    Will           *WillMsg
    Props          SessionProps  // MQTT5: receive max, topic alias map, ...
}

// 运行时：持有连接与 goroutine，不可序列化，生命周期短于 State。
type SessionRuntime struct {
    state  *SessionState
    conn   net.Conn
    out    chan *Message
    ...
}
单机实现
State 存内存，Runtime 一一对应。持久会话时 State 序列化落本地 WAL。
集群实现
State 可落复制存储、可在接管时从旧节点或存储恢复，Runtime 在新节点重建。
延后代价

会话结构体是整个 broker 引用最密集的类型。拆分它意味着协议状态机、投递、 保活、流控、持久化、指标采集全部改一遍，且极易引入并发竞态。 这条如果省了，基本等于重写 broker。

05

元数据：复制日志 + 本地全量物化视图

DAY-1

认证鉴权在 CONNECT 路径上，是吞吐最敏感的位置。契约的核心是 View() 的签名里没有 ctx、没有 error—— 它在类型层面承诺"本地内存、不会失败、不会阻塞"。这个承诺一旦写进签名， 后面任何人都不可能在连接路径上偷偷加一发 RPC。

type MetaStore interface {
    Apply(ctx context.Context, cmd Command) error // 写：走复制日志
    View() *MetaView                                 // 读：本地内存快照
}

// 签名即契约：无 ctx、无 error → 不可能是远程调用。
type MetaView struct{ ... }
func (v *MetaView) Thing(name string) (*Thing, bool)
func (v *MetaView) CertStatus(fp CertFingerprint) (CertStatus, bool)
func (v *MetaView) PoliciesFor(p Principal) []*Policy
func (v *MetaView) Revision() uint64

元数据量级很小——百万设备的 Thing + 证书 + 策略在内存里是 GB 以内， 全量驻留每个节点完全可行。写入频率低（注册、吊销、策略变更），Raft 完全够用。

单机实现
日志写本地 WAL（pebble/bbolt），视图是内存结构。与集群完全同一套读路径。
集群实现
日志走 Raft，视图由 apply 循环更新。可选外置 etcd。
延后代价

若 v0.1 写成 store.GetThing(ctx) (*Thing, error) 并在 CONNECT 里调用， 集群化时每次连接一发 RPC，握手吞吐崩塌；届时被迫重写整条认证路径并补缓存与失效机制—— 而缓存失效的正确性问题比一开始就做物化视图难得多。

06

分区单写者（Shadow / Jobs）

DAY-1

Shadow 的 version 自增、delta 计算、409 冲突判定，要求 per-thing 的单写者语义。 Jobs 的 execution 状态机同理。集群下这意味着按 thingName 分区，并把请求路由到 owner。

type Partitioner interface {
    Owner(key string) NodeID   // key = thingName
    IsLocal(key string) bool
    Count() int
}

func (s *ShadowSvc) Update(thing string, req *UpdateReq) (*Resp, error) {
    if !s.part.IsLocal(thing) {
        return s.forwardToOwner(thing, req) // 单机：unreachable，但分支必须在
    }
    return s.applyLocal(thing, req)         // 单写者，version++ 安全
}
单机实现
IsLocal 恒 true，Count() 返回 1，转发分支返回内部错误。
集群实现
一致性哈希或固定槽位；owner 变更时交接（drain + 转移）。
延后代价

Shadow 与 Jobs 服务要从"直接操作存储"改成"先判归属再决定本地或转发"， 同时所有版本自增点要重新审计并发安全性。两个服务级别的重写。

07

节点间消息传输

DAY-1

接口要在，实现可以是空的。重点是批量与背压从一开始就在签名里—— 事后把单条接口改成批量接口会牵动所有调用点和流控逻辑。

type Transport interface {
    // 批量，且返回 error 以支持背压与重试决策
    Forward(ctx context.Context, to []NodeID, batch []*Message) error
    OnReceive(fn func(from NodeID, batch []*Message))
    // Admin 扇出（契约 12 需要）
    Query(ctx context.Context, to []NodeID, q AdminQuery) ([]AdminResult, error)
}
单机实现
loopback：Forward 直接返回 nil；Query 只查本地。
集群实现
全网状长连接（gRPC 流或自有 TCP 帧），批量 + 背压 + 连接级重连。
延后代价

中等。主要风险是单条接口改批量时，上游已经按"一条一调用"写死， 吞吐优化要重做一遍。

08

禁用墙上时钟做排序与版本

DAY-1

单机下 time.Now() 用作版本号或排序键不会出错，集群下会。 这类代码散落在各处，事后排查极其痛苦，而且故障是偶发的。 立一条 lint 规则：核心包禁止直接调用 time.Now()，只能通过注入的时钟接口， 且时钟只用于超时、TTL、展示，绝不用于比较先后。

// 各类"顺序"各有专门的来源，互不混用
Shadow 版本   → 分区单写者的单调计数器
消息序号      → (NodeID, LocalSeq) 二元组
元数据版本    → 复制日志 index
会话代次      → Epoch（契约 01）
证书状态版本  → 元数据 Revision

// 允许：超时、TTL、过期、时间戳展示
// 禁止：if a.Timestamp.After(b.Timestamp) { ... } 作为正确性依据
单机实现
完全一样。单机下这些计数器都是本地变量，零额外成本。
集群实现
计数器来源变为分区 leader / Raft index，比较逻辑不变。
延后代价

需要全量审计所有时间比较点并逐一替换语义。遗漏的那几处会变成生产环境里 "偶尔 shadow 版本回退""偶尔旧消息覆盖新消息"的幽灵 bug。

09

配额的作用域必须显式

DAY-1

AWS 的配额分两类：per-connection（本地可判）与 per-account（全局）。 集群下全局配额只能"本地额度分摊 + 周期再均衡"，是近似的。 每个配额在 v0.1 就要选定走哪个方法——这个分类本身就是设计决策，不能含糊。

type Limiter interface {
    // 每连接 / 每节点：精确，无网络
    AllowLocal(key string, n int) bool
    // 每账户 / 全集群：近似，基于分摊额度；超出额度时才协商
    AllowGlobal(ctx context.Context, key string, n int) bool
}

// 走 Local：每连接发布速率、每连接订阅数、每连接吞吐、单包大小
// 走 Global：账户并发连接数、账户入站/出站速率、retained 总数、
//           共享订阅组积压、证书注册速率
单机实现
AllowGlobal 就是本地精确计数（节点数 1，分摊即全额）。
集群实现
额度按节点分摊，定期向协调者汇报与再均衡；突发时允许短时超限。
延后代价

较低但有坑：事后才区分，会发现有些限流点语义上本该全局却只在本地判， 集群下配额直接放大 N 倍，而这类问题只在压测或线上才暴露。

10

Retained 与共享订阅组是全局状态

DAY-1

两者都不是"某个连接的状态"，而是集群级状态，必须从一开始就放在接口后面， 不能直接操作本地数据结构。

type RetainedStore interface {
    Set(topic string, m *Message, v Version) error // LWW by Version，非时间戳
    Delete(topic string, v Version) error
    Match(filter string) []*Message
}

type SharedGroups interface {
    Join(group, filter, clientID string, node NodeID, persistent bool) error
    Leave(group, filter, clientID string) error
    // 选一个在线成员；集群下优先本节点成员以省一跳
    Pick(group, filter string) (SubRef, NodeID, bool)
    Members(group, filter string) []Member
}
单机实现
本地 trie / map。Pick 恒返回本地成员。
集群实现
Retained 走复制存储（量小）；组成员走兴趣传播 + 本地优先选择。
延后代价

中等。共享订阅的"选一个订阅者"若 v0.1 写成遍历本地 map， 集群下的本地优先策略、离线成员排队、组内再均衡都要重做。

11

结构化事件总线：可观测事实即事件

DAY-1

这条是管理控制台的地基，也是最容易被忽略的"不可事后加"项。 如果 broker 核心不吐出结构化事件，控制台永远无法展示断连原因、 认证失败细节、策略判定过程——因为那些信息在产生点之后就被丢弃了。 AWS 控制台在这方面很弱（只能去 CloudWatch 翻晦涩日志），这正是我们可以明显做得更好的地方。

// 一个事件源，四个消费者：$aws/events 保留主题、控制台实时流、
// 审计日志、指标聚合。绝不为每个消费者各埋一次点。
type Event interface { Kind() EventKind; Node() NodeID; Seq() uint64 }

type ConnEvent struct {
    ClientID    string
    Epoch       Epoch
    Thing       string
    Result      ConnResult      // Accepted / AuthFailed / Throttled / Evicted / ...
    ReasonCode  byte            // MQTT5 reason code
    ReasonText  string          // 人类可读，控制台直接展示
    CertFP      CertFingerprint
    CertSubject string
    AuthMethod  AuthMethod      // mTLS / SigV4 / WASM / ...
    ProtoVer    byte
    RemoteAddr  netip.AddrPort
    TLSVersion  uint16
    ALPN        string
    Duration    time.Duration   // 握手耗时，用于定位 TLS 瓶颈
}

type AuthzEvent struct {
    ClientID   string
    Action     Action           // Connect/Publish/Subscribe/Receive/RetainPublish
    Resource   string
    Decision   Decision         // Allow / ExplicitDeny / ImplicitDeny
    PolicyName string           // 命中的策略
    StatementI int              // 命中的语句下标
    Vars       map[string]string // ${iot:...} 求值结果 —— 策略调试的关键
}

type EventBus interface {
    Emit(e Event)
    Subscribe(filter EventFilter) (<-chan Event, func())
}

AuthzEvent.Vars 这一个字段，就是后面"策略调试器"能存在的原因。 策略变量求值结果如果不在判定时捕获，事后无法重建。

单机实现
进程内 ring buffer + fan-out channel。采样率可配，默认全量 Conn/Authz-deny。
集群实现
本地总线不变；控制台订阅时由 Admin 层扇出到各节点合并（契约 12）。
延后代价

埋点位置分布在协议状态机、TLS 握手回调、策略求值器内部——都是热路径与深层函数。 事后补要重新穿透多层调用传递上下文，且很多信息（如策略变量求值中间结果） 在原实现里根本没有保留，等于要重写策略求值器。

12

双 API 平面与 Admin 扇出

DAY-1

两个 API 面必须从一开始就分开：AWS 兼容面是冻结契约（为了 SDK/CLI 原样可用， 不能为了控制台的需要往里加字段）；Admin 面是我们自己的，可以自由演进、可以有流式接口。 把控制台建在 AWS 兼容面上是个单向的错误决定——之后要么污染兼容性，要么推翻重做。

/api/aws/...        AWS 兼容面：SigV4 验签、REST-JSON、错误形状对齐，契约冻结
/api/admin/v1/...   自有面：REST + SSE/WebSocket，RBAC，自由演进

// 控制台的查询天然是全集群的："列出所有在线连接"要跨节点聚合。
// 这个扇出抽象 v0.1 就要在，否则控制台会写成只认本地。
type AdminQuery interface { Scope() QueryScope } // LocalOnly | AllNodes

type AdminAPI interface {
    // 扇出 + 合并 + 分页游标（游标必须编码每节点的位置）
    ListConnections(ctx context.Context, f ConnFilter, cur Cursor) (*Page[Conn], error)
    // 实时流：合并各节点事件总线
    StreamEvents(ctx context.Context, f EventFilter) (<-chan Event, error)
    // 定向到某节点或某 clientID 的 owner
    KickClient(ctx context.Context, clientID string, reason byte) error
}

分页游标是这里的隐藏陷阱：跨节点合并分页的游标必须编码 "每个节点各读到哪"，不能是单一 offset。这个数据结构事后改要动所有列表接口。

单机实现
扇出目标只有自己；游标仍是 map 形式（只有一个条目）。
集群实现
scatter-gather + 超时降级（标注"部分节点未响应"而非整体失败）。
延后代价

控制台所有列表与流式接口要重写，游标格式变更会破坏前端分页。 若控制台已经建在 AWS 兼容面上，则要么破坏兼容性，要么整层推翻。

PART I · 共识

内嵌 Raft 的拓扑与元数据后端

决定：内嵌 Raft，不依赖外部 etcd / ZooKeeper / 数据库。 交付物是单个静态二进制。这不只是部署便利——它是相对 EMQX（需要 Erlang 集群）、 ThingsBoard（需要 JVM + Postgres + Kafka + Redis）最直接的定位优势， 也让边缘单机部署和中心集群部署共用同一个制品。

I-1

库选型

我们需要 multi-raft（几十个分区组），这一条直接决定了选型。

诚实的风险

dragonboat 的维护集中在单一作者，bus factor 是真实风险。规避方式已经在架构里了： 它只出现在 MetaStore（契约 05）和 ShardStore（契约 06）的实现体内， 上层零感知，替换成 hashicorp/raft 或 etcd/raft 是模块级而非系统级改动。 另外必须锁定 Pebble 作为日志后端以保持 CGO-free——交叉编译到 ARM 边缘设备是本项目的核心场景， 一旦引入 RocksDB 就失去了。

I-2

组的划分

三类状态，三种处理方式。最重要的一条是第三类：连接路径上不写 Raft。

组 1

元数据组 · 单组 · 所有节点持有全量

内容：Thing、Thing Group / Type、证书与状态、策略、注册模板、规则定义、Job 定义。 写入稀疏（注册、吊销、策略变更），读取极热（每次 CONNECT）。

// 关键拓扑：小 quorum + 全量副本。两者不矛盾。
投票成员 (voter)    3 或 5 个节点     → quorum 小，写延迟低
非投票成员 (learner) 其余所有 broker 节点 → 每个节点都有全量物化视图

// 于是契约 05 的承诺成立：View() 是本地内存读，无网络、不会失败。

节点数超过 5 时不要继续加 voter——quorum 变大只会让写变慢， 而我们需要的是"人人有全量数据"，learner 就能满足。

这带来的可用性优势
丢失 Raft quorum 时，设备仍可连接、订阅、收发消息—— 因为认证鉴权只读本地视图。只有注册、吊销、策略变更这类写操作失败。 "连接时查库"的设计在同样故障下会全面拒连。
组 2

分区组 · 默认 64 组 · 按 key 哈希

内容：Shadow 文档、Job execution 状态、Retained 消息。这些是有状态、需持久、需单写者的数据。

Shadow / JobExecution  分区键 = thingName
Retained               分区键 = topic

// 三件事在这里合一，这是本设计最省事的地方：
分区 Raft leader  ==  契约 06 的单写者  ==  契约 08 的版本号来源

func (s *shardFSM) Update(thing string, patch Patch) (Version, error) {
    // 由 Raft 保证本组内串行 apply，version 直接取 log index 派生，
    // 天然单调、天然跨 leader 变更安全。无需额外时钟或计数器。
    v := Version(s.lastIndex)
    ...
}

Shadow 的 version 乐观并发与 409 冲突判定， 因此是"免费"正确的——不需要额外设计，Raft 的串行 apply 已经给了。

组数选择
默认 64，可在集群初始化时设定且之后不可更改（改变哈希环需要数据迁移）。 64 组在 3–20 节点区间都合理；超大规模再考虑支持扩容重分片。
副本数
每组 3 副本，分散在不同节点。节点数 < 3 时自动降为节点数。
组 3

会话归属 · 不写 Raft · term 围栏内存租约

关键取舍

连接速率可达数千每秒，若每次 CONNECT 都写一条 Raft 日志，吞吐会被 fsync 钉死。 所以会话归属不进日志，而是由分区 leader 在内存中维护，用 Raft 的 term 做围栏。 这是 Kafka / HDFS 的经典做法。

// epoch 的高位是 Raft term，低位是 leader 本地递增序号。
epoch := Epoch(term)<<32 | Epoch(leaderLocalSeq)

// 正确性论证：
// 1. 同一 term 内，序号由单一 leader 递增 → 单调。
// 2. leader 切换后 term 严格增大，即使新 leader 从 0 开始计序号，
//    epoch 仍严格大于旧 term 的任何 epoch → 全局单调。
// 3. 旧 leader 若因网络分区仍自认 leader 并发放 epoch，其 term 较低，
//    这些 epoch 在契约 01 的校验中被拒 → 不可能双活授权。

// leader 故障转移后，新 leader 的归属表是空的：
// 处理方式是「未知即允许抢占」。这是安全的——旧持有者的 epoch 来自更低的
// term，它在下一次 epoch 校验时即被围栏淘汰。
// 代价是一个很短的窗口内可能重复投递，不会出现双重授权。
性能结果
CONNECT 路径上的分布式操作只有一次到分区 leader 的 RPC（可批量、可与同节点合并）， 零日志写入、零 fsync。
会话重注册
leader 变更后，各 broker 节点异步向新 leader 重新登记本地活跃会话， 用于加速踢出通知；正确性不依赖它。
I-3

单机即单副本

原则 01 在这里落地：单机模式不是旁路，而是副本数为 1 的 Raft 组。

节点数 1  → 元数据组 1 voter；分区组各 1 副本；归属 leader 即本机
节点数 3  → 元数据组 3 voter；分区组 3 副本
节点数 10 → 元数据组 3 voter + 7 learner；分区组 3 副本分散

// 单副本 Raft 组的开销本质上就是一个 WAL，与"直接写 WAL"相当。
// 换来的是：集群与单机共用同一条读写路径，不存在两套实现的分歧风险。

这也意味着集群功能在 v0.1 就是被持续测试的——单机 CI 跑的就是集群代码路径， 而不是等到 v0.4 才第一次让这些代码运行。这是"接口先行"之外，避免重构的第二层保险。

I-4

运维与失败模式

这些必须在 v0.1 就定义清楚语义（即便实现在 v0.4），因为它们决定了控制台要展示什么。

场景行为说明
元数据组失去 quorum 设备连接、订阅、收发 正常；注册 / 吊销 / 策略变更 拒绝 本地物化视图继续服务。控制台明确标注"元数据只读，视图版本 N"。
分区组失去 quorum 受影响 thing 的 Shadow / Jobs 写 拒绝；消息收发 正常 故障域限制在 1/64 的 key 空间。控制台需按分区展示健康度。
节点故障 其上连接断开，设备重连到其他节点；pinned 的离线队列丢失 默认后端下离线队列不跨节点保留，必须在文档首屏声明，不要含糊。
滚动升级 / 腾空节点 MQTT5 server redirect（0x9C/0x9D）优雅迁移，MQTT3 客户端走限速断开 AWS 不支持此特性，我们是超集。这是唯一优雅的再均衡手段，协议支持属 Day-1。
偶数节点集群 引入 witness（只投票不存数据）避免 quorum 浪费 dragonboat 原生支持。
脑裂 少数派无法写入；会话归属由 term 围栏保证不双活 少数派上的设备仍可收发本地消息——需在文档中明确这是有意的可用性取舍。
新节点加入 先作为 learner 同步元数据快照，追平后才接受设备连接 避免半空视图导致误拒连。健康检查需包含"视图已追平"。
I-5

元数据后端：可插拔，但读路径不可插拔

证书吊销状态这类元数据，存在哪里是可选的，怎么读是不可选的。 这个区分是本节的全部要点。

为什么读路径不能是 SQL

吊销状态不是"偶尔查一次"的数据：每次 CONNECT 要查，每条 PUBLISH / SUBSCRIBE 鉴权也要查。 按配额对齐表，这是 2 万次/秒量级的查询。任何 SQL 后端（Postgres、MySQL） 在这个位置都是错的——不是性能调优问题，是数量级不匹配。 所以契约 05 的内存物化视图不随后端变化，它是地基。后端只是 system-of-record。

于是元数据层分成两件可以独立选择的事：

system-of-record   持久化真相。写入稀疏（注册、吊销、策略变更）。可插拔
       ↓ 变更传播
materialized view  每节点全量内存视图。读取极热。不可插拔，始终内存
后端进程单条写吞吐变更传播评估
内嵌 Raft
dragonboat		 0（同进程）数千 /s tail 复制日志
推送，亚毫秒		 零外部依赖，延迟最低，apply 循环天然驱动视图更新。 缺点是元数据不能用 SQL 直接查——但这一点有解（见下）。
PostgreSQL 外部数千–数万 /s LISTEN / NOTIFY
或逻辑复制		 若要选一个"外部 SQL 后端"的首选，是它：写吞吐高一到两个数量级， 变更推送是原生能力，企业已有 DBA 运维体系。代价是 HA 要自己搭。
MySQL 外部数千–数万 /s binlog 订阅 能力接近 Postgres，变更订阅实现稍重。为已标准化到 MySQL 的组织提供。
约束 1

分区状态绝不进 SQL 后端

Shadow、Job execution、Retained 是高写入状态：单 thing 的 Shadow 配额就是 20 req/s， 上万活跃设备即数万写/秒，远超外部 SQL 后端经单条事务能承受的量级——会立刻成为系统瓶颈。

// 后端选择只作用于元数据组。分区组（I-2 组 2）始终内嵌。
元数据 (Thing/Cert/Policy/Template/Rule)  → 可插拔后端
分区状态 (Shadow/JobExec/Retained)        → 始终内嵌分区存储

// 推论：选择外部 SQL 后端时，系统里会同时存在外部数据库与内嵌存储。
// 这是外部后端的真实成本，必须在文档中说清楚，不要让用户以为
// 「配了 Postgres 就不需要本地状态了」。
约束 2

会话归属的围栏世代从哪来

内嵌 Raft 方案里，epoch 的高位取自 Raft term（见 I-2 组 3）。 换成 SQL 后端后没有 term 可用，需要等价替代——用租约表 + 条件更新做分区选举， 与 Kubernetes 的 lease 选举同款。

// 每个分区一行租约。续约频率是每几秒一次，不是每连接一次，
// 因此即便后端的写吞吐只有数百/秒也完全够用。
CREATE TABLE shard_lease (
  shard_id    INTEGER PRIMARY KEY,
  holder      TEXT    NOT NULL,
  generation  INTEGER NOT NULL,   -- 取代 Raft term
  expires_at  INTEGER NOT NULL
);

// 抢占：条件更新，仅在租约过期时成功，并递增 generation
UPDATE shard_lease SET holder=?, generation=generation+1, expires_at=?
 WHERE shard_id=? AND expires_at < ?;

epoch := Epoch(generation)<<32 | Epoch(leaderLocalSeq)

围栏正确性论证与 I-2 组 3 完全一致：generation 严格递增， 旧持有者发放的 epoch 必然更小，在契约 01 的校验中被拒。 前提是后端提供强一致的条件更新——Postgres 与 MySQL 都满足。

约束 3

变更传播要幂等且带版本

外部 SQL 后端的变更订阅（Postgres 的 LISTEN/NOTIFY 或逻辑复制、MySQL 的 binlog） 通常是至少一次语义。这决定了两件实现细节。

// 1. 视图 apply 必须幂等 —— 至少一次意味着会重复投递。
//    每条变更携带单调 revision，视图只接受 revision 更大的更新。

// 2. 变更订阅通常只在一处接入，但我们有 N 个 broker 节点都需要刷新视图。
//    所以：变更流 → 任一节点的内部端点 → 经自有事件总线（契约 11）扇出到全集群。
//    这条扇出链路同时服务「吊销后立即踢连接」，两者共用。

变更流 ──→ /internal/meta-change ──→ EventBus ──→ 各节点刷新视图 + 踢连接

// 3. 必须有兜底：定期按 revision 做一次全量校验与补齐，
//    防止变更流中断导致视图静默过期。吊销状态过期是安全问题，不能只依赖推送。
关于默认值的建议

默认且唯一的内置后端是内嵌 Raft，Postgres 与 MySQL 作为可选外部后端。 定这个默认的理由：默认配置决定了项目的第一次上手体验—— ./openiotd 直接能跑，和"先装并配置一个外部存储再跑"，对开源项目的采用率影响很大； 而且"单静态二进制、零外部依赖"是我们相对 EMQX（需 Erlang 集群）、 ThingsBoard（需 JVM + Postgres + Kafka + Redis）最直接的定位优势，默认引入外部进程就放弃了它。

外部 SQL 后端唯一的独特价值是"元数据可以用 SQL 直接查"。 而这个价值不必靠外部进程换取：内嵌模式下，物化视图可以同时落一份本地只读 SQLite 文件， 运维直接 sqlite3 查询即可，单进程与 SQL 可查询性兼得。

因此外部后端只为一种情形保留——组织已有 DBA 运维体系并要求元数据落在其统管的数据库里。 这种情形下首选 Postgres：写吞吐比任何嵌入式 SQL 方案高一到两个数量级，LISTEN/NOTIFY 是原生变更推送。 三种选择下 MetaStore 接口与上面三条约束都不变，改后端是改配置，不是改架构。 内嵌方案的完整机制见 I-6。

# 配置形态：后端可换，读路径与接口不变
meta:
  backend: embedded        # 默认。可选 postgres | mysql
  embedded:
    voters: 3              # 其余节点自动成为 learner
    sqlite_view: ./meta.db # 可选：导出只读 SQLite 供 SQL 直查
  postgres:
    dsn: ...
    read_consistency: primary # 仅用于 system-of-record 读，热路径永不经过
    change_feed: listen_notify
  mysql:
    dsn: ...
    change_feed: binlog
view:
  resync_interval: 30s     # CDC 中断时的兜底全量校验
I-6

零外部依赖下的跨节点证书一致性

以"吊销一张证书"为例，走完内嵌方案的端到端链路。 这一节是 I-5 表格里"内嵌 Raft"那一行的展开。

关键认识

Raft 日志本身就是全序广播通道。每个节点（含 learner）独立 apply 同一条有序日志， 因此吊销命令抵达时，各节点各自踢掉自己持有的连接，不需要任何额外的失效通知机制。 外部存储方案反而要在上面再搭一层扇出（CDC webhook → 自建转发 → 各节点）， 多一个组件、多一处可能静默失效的环节。

吊销的端到端流程

1. 运维在任意节点调用 UpdateCertificate(fp, REVOKED)
2. 该节点若非 meta leader，把提案转发给 leader（并代持响应）
3. leader 追加一条命令进 meta Raft 日志：
       Cmd{Op: OpSetCertStatus, Fingerprint: fp, Status: REVOKED, Reason: ...}
4. 多数派 fsync 提交   本地 NVMe ~1–5ms；跨可用区 ~10–30ms
5. 每个节点（voter 与 learner 一致）在自己的 apply 循环里执行：
         ├─ 更新热内存视图，revision = 该条日志的 index
         ├─ 写入 Pebble 冷存（持久真相）
         └─ 向本地 EventBus 发出 MetaChange 事件
6. 各节点的吊销处理器消费本地事件 → 遍历本节点连接，
       踢掉所有使用该指纹的会话，DISCONNECT reason = 0x87 Not authorized

// 全程没有节点间的额外消息。广播由第 4、5 步的日志复制完成。

为什么"每节点全量"在内存上是可行的

容易被误判的一点是"全量元数据驻留每节点会吃光内存"。实际上热路径只需要元数据的一个极小子集—— 鉴权要的是指纹到状态、指纹到策略集、以及策略变量用到的那几个字段，不是完整的 Thing 记录。 于是分成两层：

// 热层：内存，紧凑，鉴权路径只碰这里
certStatus    map[[32]byte]CertState        // 指纹 → 状态；百万证书 < 100MB
certToPolicy  map[[32]byte]policySetID      // 策略集去重后通常只有数十到数千个
policySets    []*CompiledPolicySet          // apply 时预编译，不在消息路径上解析 JSON
thingHot      map[string]*HotAttrs          // 仅策略变量实际引用的字段

// 冷层：Pebble，按需读取，不在热路径上
完整 Thing 记录 / 证书元数据 / 开通模板 / 规则定义 / 分组层级 / 审计

// 量级：百万设备约 100MB 级，千万设备约 1GB 级 —— 全量驻留可行。

安全要点

陈旧视图必须 fail-closed

超集

这是自建场景独有、而 AWS 不存在的问题：网络分区中的少数派节点，其视图冻结在最后提交的 index 上， 可能仍然接受一张在多数派侧已被吊销的证书。托管服务只有一个控制面，不会有这个问题。

// 吊销是安全语义，不能无限期容忍陈旧。
// 热视图记录「最后一次确认追平的时间」，超过阈值即对新连接关闭。

if time.Since(v.LastConfirmedAt()) > cfg.MaxViewStaleness {
    // 拒绝新连接（fail-closed），但不断开已有连接 ——
    // 否则一次控制面故障会放大成全网设备掉线。
    return ErrViewStale
}

默认阈值建议 30s，可配。这条取舍要在文档里明确写出来： 吊销的传播上界等于这个阈值，而不是"立即"。诚实声明边界比含糊的"实时吊销"更可信。

为什么不断已有连接
控制面故障不应该放大成数据面全网掉线。 已连接设备继续工作，新连接 fail-closed，是正确的失败方向。
配套
视图陈旧度作为节点健康检查的一部分；控制台在集群视图里直接展示各节点的视图版本偏差。

PART I · 边界

可以安全延后的部分

同样重要的是说清楚什么不必现在做。以下都只是"换实现体"，不改签名、不改数据结构形状， 延后到 v0.4 的成本接近于零。把精力花在这些上面是 v0.1 的主要浪费来源。

延后不产生重构

  • 共识库选型（dragonboat / etcd-raft / hashicorp-raft / 外置 etcd）—— 藏在 MetaStore.Apply 后面。
  • 节点发现与成员管理（静态列表 / gossip / Kubernetes API / DNS SRV）—— 独立模块，无上游依赖。
  • durable session 的具体后端（本地 WAL / 复制日志 / 外置 NATS、Redis、Kafka、FoundationDB）。
  • 兴趣传播的具体编码（全量 filter 列表 / bloom / cuckoo 摘要）—— 只要 Match 签名不变。
  • 跨节点共享订阅的负载均衡算法（随机 / 轮转 / 最少积压 / 粘性）—— Pick 的实现细节。
  • 再均衡策略（何时用 MQTT5 server redirect 迁移连接）—— 但 0x9C/0x9D 的协议支持本身属于 Day-1。
  • 多可用区 / 多地域拓扑、跨集群桥接（bridge / MQTT over MQTT）。
  • 控制台的图表与交互细节 —— 只要契约 11、12 的数据面在，前端可以独立迭代。

PART III

管理控制台

目标不是"也有一个后台"，而是在几个具体位置明显超过 AWS 控制台。 超越的机会分两类：一类是 AWS 结构上做不到的（托管服务不暴露节点与集群内部）， 一类是 AWS 做得确实差的（策略调试、断连归因、实时视图）。两类都值得做，但要分清。

III-1

AWS 控制台的实际短板

先诚实评估对手，再谈超越。以下是 IoT Core 用户反复抱怨的点。

  • 策略调试几乎不可能。连接被拒只得到一个泛化的授权失败，既不告诉你哪条语句未命中， 也不告诉你 ${iot:...} 变量求值成了什么。这是 IoT Core 的头号痛点。
  • 断连原因要去 CloudWatch 翻日志，且原因字符串晦涩、与控制台割裂。
  • 没有实时视图。看不到当前在线连接列表、看不到实时消息流（内置 MQTT 测试客户端功能很弱）、 看不到订阅分布。
  • 没有节点与集群视图——这是托管服务的本质限制，不是疏忽。自建场景下这恰恰是运维最需要的。
  • Shadow 只展示原始 JSON，没有 desired/reported/delta 对照，没有历史。
  • Jobs 只给汇总计数，失败分布与单设备下钻需要自己拼 API。
  • 导航层级深、批量操作弱、检索要单独开启 fleet indexing、无深色模式。
III-2

架构约束

五条约束，全部由 Part I 的契约决定。先立约束，再谈功能，否则控制台会在集群化时推翻重做。

  • 内嵌，不单独部署。前端产物经 go:embed 打进同一个二进制。 零额外进程、零额外依赖——与"单静态二进制"的整体定位一致。支持反向代理子路径与禁用开关（边缘部署常需关闭）。
  • 只走 Admin 面。控制台的全部请求指向 /api/admin/v1，绝不触碰 AWS 兼容面（契约 12）。 这保证了兼容面契约可以冻结，控制台可以快速迭代。
  • 实时数据走流式。指标与事件用 SSE（单向、可穿透代理、自动重连）， MQTT 抓包用 WebSocket（需双向）。轮询只作为降级。数据源是契约 11 的事件总线。
  • 百万设备列表必须服务端分页与检索。依赖 I 节的检索索引，前端只做虚拟滚动。 任何"拉全量到前端过滤"的实现都是错的——这是此类控制台最常见的致命设计缺陷。
  • 跨节点聚合要能部分失败。scatter-gather 超时的节点在 UI 上标注为"N 个节点未响应"， 而不是整个页面报错。运维工具在故障时必须仍然可用——这正是最需要它的时刻。

前端技术栈

选型标准：产物要小（嵌进二进制）、密集表格与高频时序图要快、不引入重型组件库。

关注点选择理由
语言与构建TypeScript + Vite构建产物可控，go:embed 友好。
框架React生态（尤其表格与虚拟滚动）成熟度决定的务实选择，不是偏好。
数据层TanStack Query分页游标、缓存失效、SSE 增量合并都有现成模式。
表格TanStack Table + Virtual百万行虚拟滚动 + 服务端分页，这是硬需求（III-2）。

组件与样式Radix 原语 + 自有样式只取无样式的可访问性原语，避免整套设计系统的体积与风格绑定。
主题深浅双主题，token 驱动运维人员长时间盯屏，深色模式不是装饰。
PART IV

验收门槛

"实现了协议"不是验收标准。官方 AWS Device SDK 的示例不改一行能跑通才是。 这套对照测试要在第一周就搭起来——它既是护城河，也是唯一能让人相信兼容性声明的东西。

IV-1

兼容性对照套件

同一套官方示例，分别打 AWS 与本服务，diff 行为。差异要么修复，要么登记为已知差异并出现在矩阵里。

  • 设备 SDK：aws-iot-device-sdk-python-v2、-js-v2、-cpp-v2、 -java-v2、aws-iot-device-sdk-embedded-C。覆盖 pubsub、shadow（含命名影子）、 jobs、fleet provisioning、共享订阅、MQTT5 各示例。embedded-C 必须过——它走 CBOR 且对协议细节最敏感。
  • 控制面：aws CLI 与 boto3 指向本服务，跑完整的注册 → 签发 → 附策略 → 连接 → 吊销流程。
  • 协议一致性：OASIS 一致性条款逐条、Paho 互操作测试、与 mosquitto / EMQX 的交叉验证。
  • 解码器 fuzz：Go 原生 fuzzing 持续跑 internal/mqtt/packet，语料库入库。 畸形包处理是这类项目的 CVE 高发区，而 broker 暴露在公网。
  • 集群正确性：故障注入测试——杀节点、网络分区、时钟跳变、Raft leader 频繁切换下， 验证同一 clientId 绝不双活、Shadow 版本绝不回退、离线队列行为符合声明。 这类测试 v0.1 就要存在（单副本也能跑出 epoch 校验路径）。
  • 性能基线：emqtt-bench / mqtt-stresser 可复现脚本 + 硬件规格 + 原始数据公开。 不发布无法复现的数字。
IV-2

v0.1 的完成定义

范围必须窄且硬。下面这些全绿才叫 v0.1，少一条都不发。

  • MQTT 3.1.1 + 5.0 全功能（含 QoS 2 超集），8883 / 443-ALPN / WSS-SigV4 三个端点。
  • 内嵌 CA 签发与 CSR 签发；证书状态机；吊销即时断连。
  • IoT Policy 求值含全部策略变量；策略调试器可用。
  • 完整 Device Shadow（经典 + 命名，含 metadata 逐叶子时间戳与 409 冲突）。
  • 连接与订阅生命周期事件；Prometheus + OTel；结构化审计日志。
  • 控制面 ~40 个 action + 数据面全部；aws CLI 与 boto3 可直接使用。
  • 控制台：总览、设备、实时连接、MQTT 测试客户端、策略调试器、单设备时间线、RBAC、中英双语。
  • 十二条 Day-1 契约全部落地，六条 CI 规则全部开启，单机 CI 跑在 1 副本 Raft 组上。
  • 官方 SDK 对照套件绿灯，fuzz 持续运行无 crash。
IV-3

主要风险

风险量级应对
范围爆炸高 AWS IoT 是十几个子服务。本矩阵就是应对手段——公开声明 profile， 拒绝在 v0.1 做任何标为路线图的东西。
人力与可持续性高 到可信的 v1.0 约 2–5 人年。这是本项目最可能的死因，不是技术。 要么把 v0.1 砍到极窄并做到无可指摘以吸引贡献者，要么尽早确定组织与资金形式。
控制台拖慢内核中 UI 工作量容易失控。约束：契约 11 与 12 的数据面做好后， 前端可独立迭代；内核不为 UI 需求让步，更不污染兼容面。
dragonboat 单一维护者中 已隔离在 MetaStore / ShardStore 之后，可模块级替换。 锁定 Pebble 保持 CGO-free。
法律与命名中 API 层面做兼容实现本身没问题（botocore 的 service model 是 Apache-2.0，可用）； 不得抄 AWS 文档原文，宣传上使用"AWS IoT Core–compatible API"这类措辞， 避免暗示背书。许可建议 Apache-2.0。
性能声明失信中 只发布可复现的基准（脚本 + 硬件 + 原始数据）。 单节点连接数的真实瓶颈是 TLS 每连接缓冲区，不是 goroutine——不要给出做不到的数字。
