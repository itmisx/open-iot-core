# 设备 SDK 对照测试

用**真实的设备 SDK** 对跑一个真实节点，而不是用我们自己拼的客户端。

区别是实质性的：自己拼报文只能验证"我以为的协议"，验证不了设备上实际
跑的那套代码。本目录的两个缺陷都是这么发现的，而 Go 侧测试当时全绿：

- **私钥 PEM 编码**：签发的 EC 私钥是 PKCS#8，AWS SDK 在 Apple 平台上
  读不了，报一条完全指不到原因的 `AWS_IO_FILE_VALIDATION_FAILURE`。
  Go 测试只检查"自己发的自己能解析回来"，永远过。
- **遗嘱**：只在 MQTT 5 的 DISCONNECT reason 0x04 时发出，也就是只在
  客户端主动请求时才发。掉电、断网、保活超时一律静悄悄——而那正是
  遗嘱存在的理由。当时唯一的遗嘱测试恰好覆盖了唯一能工作的那条路径。

## 跑

```bash
./tests/device-sdk/run.sh
```

它自己建一个临时数据目录与节点（端口 28883 / 28443 / 29090），跑完删掉，
不碰 `.demo/` 与 `./data`。需要 Python 3.9+ 与一次 pip 安装。

```bash
WITH_KEEPALIVE=1 ./tests/device-sdk/run.sh   # 加测保活超时，多花约 45 秒
```

## 为什么不进 `make gate`

门禁必须只依赖 Go 工具链（NFR-050、LANG-019 的同一条取向）：`go install`
不该要求先装 Python 与一套 C 扩展。这套测试的定位是**发版前与改动接入层
之后手动跑一次**，以及 CI 里单独的一个可选 job。

它与 Go 测试是互补而非替代：Go 测试跑得快、覆盖得细、能注入时钟；
这里只回答一个问题——真实设备连得上吗。
