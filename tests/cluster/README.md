# 三进程集群验收

```bash
bash tests/cluster/run.sh              # 跑一遍，跑完拆掉
KEEP_WORK=1 bash tests/cluster/run.sh  # 保留数据目录、日志与复制日志
BASE_PORT=51000 bash tests/cluster/run.sh
```

`make cluster-test` 是同一条命令。脚本自己建复制 CA、签三张节点证书、
init 三个数据目录、起三个 `openiotd serve`，跑完删掉。

## 为什么要有这套

`internal/meta` 的 `TestReplicatedStore*` 用的是进程内的共识组，三个节点
共用一个进程的内存。它证明不了「三个进程用 TLS 复制同一条日志」。
这里验的每一条都只有在真进程上才会失败：

- 冷层记录（设备属性、策略正文）在三个节点上一致（CLU-065）
- 策略文档随日志走，各节点各自编译（CLU-064）
- 跟随者的写入转发给 leader，并且等到本节点应用了才返回（CLU-071）
- 三个节点的 `metaRevision` 相同（OBS-146）
- 掉一个节点写入照常；再掉一个失去多数派，写入返回 **503** 而读取照常
  （CLU-042、CLU-073）
- 起**第四个节点**并加入运行中的集群：四个节点都看到 4 个成员、多数派
  从 2 变成 3、新节点追平既有数据，移出后多数派回到 2（CLU-090 至 CLU-095）
- 复制日志真的落在 data dir 的 `raft/` 下

不进 `make gate`：门禁只依赖 Go 工具链，而这套要 openssl、要起三个进程
等选举（与 `tests/device-sdk` 同一条理由）。

## 配置长什么样

脚本生成的 `*.yaml` 就是最小的集群配置。注意三点：

1. **复制证书的 CommonName 必须是节点 ID**，SAN 要含 `localhost`
   （CLU-069）。拨号侧以主机名校验链，节点身份由 CommonName 单独认。
2. `cluster.replication.peers` 是**初始**成员名单，须含本节点自己，
   且条数要等于 `cluster.voters`。成员变更之后以复制日志为准，这份
   不用跟着改（CLU-090）；脚本里第四个节点 d 的 peers 只写它自己，
   其余节点的配置一个字没动。
3. 第一个节点 `mode: bootstrap`（它发起选举），其余 `mode: join` 并给
   `node.seeds`。单机写了 `cluster.replication` 会被配置校验拒掉
   （CLU-070）——那份配置看起来像集群而进程其实是单机。

## 已知的坑

- 第一版把 `api()` 写成不带 `--fail-with-body` 的 curl，于是「跟随者写入
  返回 500」被当成成功，失败落在下一条断言上，指向完全错误的地方。
- `metaRevision` 那条断言第一版用 `sed` 抽字段，而响应是缩进 JSON——
  抽到三个空字符串，`sort -u` 得出一行，断言在**什么都没比**的情况下
  通过了（TST-116 记过同一个反模式）。现在用 `json.load` 解析，并且
  抽不到就当失败。

## 验收覆盖的那几条

| 验的东西 | 需求 |
| --- | --- |
| 冷层记录（设备属性、策略正文、计数器）在三节点一致 | CLU-065 |
| 策略文档随日志走，各节点各自编译 | CLU-064 |
| 跟随者的写入转发给 leader，并等到本节点应用了才返回 | CLU-071 |
| 三节点 `metaRevision` 相同 | OBS-146 |
| 跨节点消息投递（b 订阅、a 发布） | CLU-062、CLU-075 至 CLU-080 |
| 影子在三节点一致（含版本号），版本冲突仍是 409 | CLU-082、CLU-083 |
| 同一 clientId 连到另一个节点时旧连接被断、新连接健康 | CLU-081 |
| 掉一个节点写入照常；失去多数派写入 503 而读取照常 | CLU-042、CLU-073 |
| 从第三个节点列举到连在另两个节点上的连接，前缀筛选也跨节点 | CLU-086 至 CLU-089 |
| 第四个节点加入运行中的集群、追平数据，多数派随之变化 | CLU-090 至 CLU-095 |
| 保留消息跨节点（含清除后不复活：墓碑随广播传播） | MQTT-122 至 MQTT-124 |
| **持久会话与离线队列跨三个节点** | CLU-111 至 CLU-117、TST-160 |
| 复制日志落在 data dir 的 `raft/` 下 | — |

会话那一段的形状值得单独说，因为它是这套脚本里唯一分两次调用的：

```
session.py prime   设备在 a 上以 clean session = 0 订阅、干净断开，
                   再从 b 的管理面发一条 QoS 1（经兴趣通告转给 a 入队）
session.py verify  设备连到 c —— CONNACK 必须报 session present = 1，
                   且必须收到那条排队的消息
```

**用第三个节点而不是回到 a**：c 从没见过这个设备、也没有它的订阅，所以
两件事都只能来自复制。分两次调用是为了让编排能在中间插入「杀掉入队的
那个节点」——那是「离线队列不再钉在节点上」的真判据（k8s 上那一轮就是
这么验的）。

脚本里还有两件事是顺带被验证的：设备证书只在 a 上签发并登记，而 b 要能
认出这台设备才可能让它连上来（证书登记随日志走）；三个节点共用同一份
设备 CA 的那一步模拟了真实部署里「把同一份 CA 分发到各节点」。

## 再一个坑

运行中的节点**不能**用离线的 `cert issue` 签发证书：那条命令直接写本节点
的冷层，不经复制日志，于是别的节点上根本没有这张证书。第一版的扇出验收
就是这么失败的，症状是 CONNECT 原因码 5——看起来像策略写错了。
脚本现在走 Admin API 签发（那条路径经日志），并且先建设备再签证书。

- 加第四个节点那段第一版忘了把 d 登进 `NODES`/`ADMIN_PORTS`，于是 `api 3`
  取不到令牌，报的却是 `unbound variable` 加一个 401——错误信息指向
  shell 而不是指向集群。往这类按下标取配置的脚本里加节点时，先确认
  每一张并行数组都加到了。
