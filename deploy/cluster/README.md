# 三节点集群

元数据（设备、证书、策略）经 raft 多数派复制，消息跨节点投递，影子各节点
算出同一个版本号。

| | 什么时候用 |
| --- | --- |
| [`compose/`](compose/) | 在**一台机器**上起三个容器，用来看集群怎么复制、怎么失效。**不是**高可用——机器一挂全没 |
| [`k8s/`](k8s/) | 跨机三节点，真正的高可用。三个 Pod 必须落在不同故障域 |
| [`k8s-million/`](k8s-million/) | 五节点×20万连接的容量起点：固定五成员、RF=3、资源请求与MQTT专用LoadBalancer。仍须五机实测 |

先读 [`../README.md`](../README.md) 的「开始之前定两件事」、「通用约定」与
「四处踩进去不报错的地方」，这里只写集群特有的。

## 为什么是三个

多数派是 `成员数/2+1`：

| 成员数 | 多数派 | 能同时掉几个 |
| --- | --- | --- |
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 2 | **1** |
| 4 | 3 | 1 |
| 5 | 3 | **2** |

这个数字由 `GET /api/admin/v1/cluster/members` 的 `quorum` 字段给出，
随成员变更而变——成员变更之后它不再等于配置里的 `voters`。

两个节点不比单机强（掉一个就写不了）。**四个不比三个强**——扩到偶数只是多
花一台机器。要容忍两个节点同时故障得上五个。

丢掉多数派时：**写入返回 503，读取照常**（CLU-042 的取舍）。503 而不是 400
是有意的——请求本身合法，是此刻做不了（CLU-073），客户端据此重试，而 400
会让它放弃。设备的连接、订阅、收发都不受影响，直到超过
`cluster.max_view_staleness` 之后新连接才 fail-closed。

## 集群能做到什么，做不到什么

对外宣称前照这张表核一遍。

| 能力 | 状态 |
| --- | --- |
| 元数据（设备、证书、策略）跨节点复制 | 有，raft 多数派提交 |
| 自动选举与故障转移 | 有，leader 挂掉后剩余多数派自行选出新的 |
| 消息跨节点投递 | 有。阶梯量出的零丢弃上限（2026-11-22）：跨节点 **12 万**条/秒、同节点 **15 万**条/秒（均为**三节点合计**，不是单节点），跨节点扇出 10 万条/秒。跨节点那个 12 万是**下界**：更高的每一级都有订阅者被断开，本轮没压出上限。此前低一档（6 万）的原因是转发同步发生在发布者的读协程上、一条消息一次问答；CLU-139 改为按对端异步合批后这一档基本消失（CLU-038、CLU-120 至 CLU-124、CLU-139）。数字与全部阶梯级见 `docs/baseline/throughput.md` |
| Device Shadow 跨节点一致 | 有，各节点算出同一个版本号。吞吐按并发阶梯量（2026-11-22）：**这一栏随并发涨**，三节点并发 1 只有 46.6 条/秒而并发 200 时在 456 到 1,476 之间（四个样本差 3.2 倍，**单机三进程量不出上限**），拿低并发的单点当容量会低估一个量级。单节点相反，恒在 111–119 条/秒（被串行化，已知缺口）。开 `shadow_shards` 在单机上反而更低（共用一块盘），其收益须在各节点独立磁盘上验。影子、建设备、签证书都在这条复制日志上；设备数据面不在 |
| 跨节点共享订阅组 | 有，组内只投一个成员 |
| 「列出在线连接」跨节点聚合 | 有，单节点失败标 `partial` 而不是整体失败 |
| 加减节点不重启 | 有，走 `POST /api/admin/v1/cluster/members` |
| 同一 clientId 的跨节点互斥 | **最终一致**，窗口是一次 mesh 往返，不是零窗口 |
| 跨节点的读写可见性 | **一次复制往返**，不是零。写完立刻读跟随者可能 404 |
| 保留消息跨节点 | **最终一致**（2026-11-19 接上）。经 mesh 广播同步，不进共识；生效窗口是一次广播，不是零——A 写完、B 上的订阅者在广播到达前订阅，收到的是旧值或空。另外广播丢了且该主题此后不再发布时，那个节点会一直缺这一条（看 `retained_broadcast_dropped` 指标），按主题分桶的 digest 对账排在下一步 |
| 离线 QoS 1 队列 | **跨节点复制**（2026-11-20 接上）。经会话分区组的 raft 日志复制，节点故障时队列不丢。有上限：每会话 100 条，满了丢新的（QTA-111） |
| 集群下的建连速率 | **按会话类型分档。** 非持久会话（3.1.1 clean session）的已发布基线是 **23,540** 条/秒、p50 10.25 ms（2026-11-22，3 轮中位数，区间 22,828–24,249）：这条路径零会话写（CLU-128）。上一版同参数是 26,028 条/秒，与本版区间重叠、属同档。接全局 ownership 后的同机单轮是 **22,707** 条/秒、p99 62 ms，换来的是跨节点 epoch 真正可比。持久会话的已发布基线是 **3,227** 条/秒、p50 497 ms（2026-11-22，3 轮中位数，区间 2,976–3,270，6,000 条并存、**并发 2048**；同参数并发 256 只有 1,156，这一栏不压到足够并发就量不出来）——比非持久低一个量级是机制决定的：过期间隔大于 0 的会话每次建连要提一条复制日志并等它提交。更早一版同参数是 205 条/秒；CLU-134 合并 Raft 提案、CLU-137/138 接 ownership 并合批后，1024 并发同机单轮是 **1,476.1** 条/秒、p99 886 ms、零拒绝。上述新数字均是归因单轮，待重跑多轮后再更换发布基线。设备总数不受影响，受影响的是重连风暴的收敛时间；生产仍应用 `connect_rate` 配额削峰，并看 `owner_claim` / `session_write` 分段耗时 |
| 持久会话连不上时的行为 | 复制层写不进去（没有 leader、失去多数派、提案超时）时**拒绝连接**，CONNACK 回 `ServerUnavailable`，而不是回成功然后把会话丢掉（CLU-130）。设备按退避重连即可。看 `connections_total{result="StoreFailed"}` |
| 持久会话跨节点 | **有**（2026-11-20 接上）。设备连到另一个节点仍是同一个会话：订阅、属性与离线队列都在。复制的不含在途消息——那些会重传而不是丢（CLU-113） |
| 会话的跨节点可见性 | **一次复制往返**，不是零。A 上断开后立刻连 B，B 有可能还没应用 A 的最后一次写入（CLU-116） |
| 会话围栏（同 clientId 的新旧之分） | **已在跨节点生效。** 会话分片 leader 以真实 Raft term 与 term 内序号发放 epoch，远程 Claim 按分片合批，零日志、零 fsync。新 owner 会精确通知前 owner 驱逐旧连接；即使驱逐通知丢失，旧 epoch 的会话写也会被存储围栏拒绝。`session_write_stale_total` 现在表示真实接管竞态，对应 CONNECT 会被拒绝。见 CLU-137/CLU-138 |
| 一个节点挂了，它上面的离线队列 | **还在**，其余节点有全量。但它挂着期间**新发给那些设备的消息不再入队**——入队要本地路由表里有那个订阅，而那只有它上次接入的那个节点才成立（MQTT-128） |

## 会话分片数（`session_shards`）

会话与离线队列不走元数据那条日志，而是按 `clientId` 哈希分到若干条独立的
raft 日志上（CLU-111）。默认 8 条，三份清单都不写它。

```yaml
cluster:
  replication:
    session_shards: 8     # 0 或省略 = 默认 8，上限 64
```

**它一经初始化不得更改。** 分片号参与「哪个分片拥有哪些会话」的判定，改了
之后既有会话会被算到别的分片上，而那条日志里没有它们——症状是「集群里
一部分设备的持久会话忽然不见了」，而且取决于设备名，看不出规律。要改只能
把三个节点的数据目录一起清掉重建。

**它不是 `cluster.shard_count`。** 后者是路由用的虚拟分区数（默认 64，
影子的分区键按它取模）；这个是真实的 raft 日志条数，64 条意味着 64 套
心跳与 fsync，那是把节点压死而不是提高吞吐。两个名字相近的数不是一回事。

调大的收益是会话写入吞吐线性增长（它跟着「发给离线设备的消息」走，不是
全部消息），代价是心跳与 fsync 的放大也线性增长。按节点核数相称地配。
本机五进程共享一块盘的 6,000 条持久 mTLS A/B 中，16 条两轮为 1,937 / 1,653
CONNECT/s，而相邻 8 条为 1,644；尾延迟方向较好但吞吐离散不足以改默认值。
百万新集群应在正式初始化数据目录前，用五台独立磁盘分别压 8 与 16 后再定，
不要在已有数据上直接改这个值。

## 影子分片（`shadow_shards`）

新建集群的示例启用 8 条独立影子 Raft 日志，避免设备影子写入继续与证书、
策略等元数据争抢同一条日志：

```yaml
cluster:
  replication:
    shadow_shards: 8
    shadow_replication_factor: 3
```

`shadow_shards: 0` 或省略会继续走旧 metadata 日志，用于先滚动升级二进制；
上限 14。两个值会写入 `shadow-layout.json`，初始化后不可直接修改。旧集群启用
时必须先升级全部节点、停掉写流量，再在所有节点同时写入相同配置后重启；不得
让启用与未启用的节点混跑。五节点 RF=3 时，每个影子只驻留三个副本；Get/List
会在副本间安全回退，写请求发生模糊网络失败时不会换节点重发。

## 三条铁律

**1. 复制链与设备 CA 是两条独立的信任链**（CLU-068）。

共用的话，拿一张设备证书就能冒充一个节点——等于把元数据写入权发给了任何
一台设备。两种清单里的证书脚本都生成两套 CA，别去合并它们。

每张节点证书的 **CommonName 必须等于节点 ID**（CLU-069），复制层就是靠它
认对端身份的。CN 对不上的后果是握手被丢掉，而日志里看起来像网络问题。

反过来，**不要给节点证书签上拨号用的主机名**（CLU-103）。拨号侧根本不校验
SAN：它自己用复制 CA 建链、再比 CommonName（CLU-102）。两份清单的证书脚本
因此只签 CN——k8s 那份的 SAN 是 Pod 名，而拨号名是
`openiotd-N.openiotd-peers`，刻意对不上。对得上的话，一个「又按主机名校验
了」的回归就不会在清单上显形，而它上一次的表现是三个 Pod 一致地报「对端
不可达」，指向网络而不指向证书。

**2. 三个节点必须共用同一套设备 CA**（NFR-103）。

设备证书由任一节点签发，而设备可能连到任意一个节点——各节点自备 CA 的话，
一台设备只能连上签发它的那个，其余节点 mTLS 直接握手失败。两种清单的初始化
都包含「把第一个节点的设备 CA 分发给其余节点」这一步，别跳过。

由此也**不要给集群里的节点设 `OPENIOTD_AUTO_INIT`**（那个开关见
[`../README.md`](../README.md)，单节点的清单用它，集群不用）。它让容器在
`serve` 之前自己 init 一次，于是每个节点各建一套设备 CA——正是这条铁律禁止
的情形，而且是静默发生的：数据卷被清掉之后，带着它的节点会若无其事地起来，
症状要等到设备连上第二个节点才出现。

两份集群清单的初始化之所以必须单列一步，根子也在这里：那一步不只是建目录，
还要**把第一个节点的设备 CA 分发给其余节点**，而这件事没有任何「每个节点
自己做一遍」的版本。顺带一句，k8s 那份的主容器覆盖了镜像入口
（`command: ["/bin/sh", "-ec"]`），这个变量在那里不起作用；compose 那份
会起作用。

**3. 要让重连设备切换节点后恢复 TLS session，所有 MQTT TLS 监听器还要共享
session ticket 密钥环。** 这是性能选项，不配不影响正确性；不配时 Go 为每个
进程维护随机 ticket key，设备只能在回到原节点时恢复。

```yaml
listeners:
  mqtt_tls:
    session_ticket_keys_file: /run/secrets/openiot-ticket-keys
```

文件每行 64 个十六进制字符（32 字节）。第一行签发新 ticket，后续行只解旧票据。
轮换按「新、旧」两行先滚到所有节点，等旧 ticket 生命周期过去后再删第二行，
否则滚动发布期间一部分节点会突然恢复失败。该文件能让持有者解开整个集群签发的
ticket，密级按集群 Secret 管理，不能进镜像或 Git。五节点强制把第二波连接移到
下一节点的实测恢复率是 1,500/1,500；恢复后仍会重新检查证书吊销与设备策略。

**4. 复制地址必须跨重启稳定，每个节点要有一个固定的副本号。**

共识库把节点的复制地址记进数据目录，换了地址再启动会直接报
`not the owner of the data directory`。compose 用服务名、k8s 用 Pod 的稳定
DNS 名，两者都满足；但"改一下 `cluster.replication.addr` 再重启"从此是
**起不来**的操作，而不是改了就生效。

`cluster.replication.replicas` 给每个节点一个 `uint64` 副本号——共识层按它
认成员，而本项目的身份是字符串节点 ID。三个节点的这张表必须完全一致，
且与 `peers` 的键集合相同；不一致在启动时就被拒。**不要改成从节点 ID 哈希
推导**：撞号之后两个节点会抢同一个共识身份，表现是日志复制错乱，而日志
里看不出跟节点 ID 有关系。

加节点时要把新节点的副本号一起给出（见「加减节点」），leader 无从知道它。

## 备份与恢复

共通的那半在 [`../README.md`](../README.md)（备份对象、为什么它的密级
等于整套系统的密级）。集群特有的是这几条：

- **要备的是每个节点各自的数据目录**（compose 三个卷、k8s 三个 PVC）。
  三份不等价：设备 CA 与管理面令牌三份相同，但 raft 日志与元数据各有自己
  的进度。会话与离线队列自 2026-11-20 起是复制的（见上面那张表），所以这
  一项三份等价——但它们在**会话分片**那几条日志里，与元数据同一个数据目录，
  备份时不必分别处理。
- **复制链的 TLS 材料不在数据目录里**，要单独备份：compose 是 `pki/`，
  k8s 是 Secret `openiotd-repl-tls`。丢了可以重签，但 CommonName 必须仍然
  等于各节点的节点 ID。
- **单独恢复一个节点是起不来的。** 它的成员列表里仍是三个（成员列表在
  raft 状态里，随快照传播），一个成员凑不出多数派；而「把另外两个移出去」
  本身也是一次写入，同样要多数派才能提交。所以恢复要么三个节点一起恢复
  （各自的备份越接近同一时刻越好），要么保住多数派、只把坏掉的那个节点
  当成**空节点**重新加进来，由快照追平（CLU-059）——后者是正常运维路径，
  也是这套清单真正验过的那条。
- 本项目没有「从单份备份重建集群」的命令（共识库的 recover 入口
  没有对外暴露）。**这条路径没有验收覆盖**：`make cluster-test` 验的是运行
  中的故障与故障转移，不验备份恢复。上生产前请在测试环境自己走一遍。

## 加减节点

配置里的 `cluster.replication.peers` 与 `cluster.voters` 只是**初始**成员，
加减节点**不改它们**，走 Admin API（CLU-090），之后以复制日志为准。
照着配置去「修」成员列表是错的。

```bash
# 当前成员、各自地址、多数派票数，以及现在谁是 leader
curl -s -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:9090/api/admin/v1/cluster/members

# 加。replicaId 必须与新节点自己 replicas 里写的那个相同——
# 共识层按它认成员，而 leader 无从知道新节点配了几号（铁律 3）。
curl -sf -H "Authorization: Bearer $TOKEN" -X POST \
  -H 'Content-Type: application/json' \
  -d '{"id":"node-d","addr":"node-d:7946","replicaId":4}' \
  http://127.0.0.1:9090/api/admin/v1/cluster/members

# 减
curl -sf -H "Authorization: Bearer $TOKEN" -X DELETE \
  http://127.0.0.1:9090/api/admin/v1/cluster/members/node-d
```

几条约束：

- 新节点自己的配置里 `peers` 只需写它自己。它的地址随成员变更复制给其余
  节点，别人的地址随日志复制给它。
- **一次只能有一个成员变更在途**，上一次提交完才能开始下一次。
- 新节点要先有一张 CN 等于它节点 ID 的复制证书，否则它连不进来。
- 扩容的顺序是「先备好证书 → 再起进程 → 再加成员」；缩容反过来，
  **先** `DELETE` 成员**再**停进程。顺序反了会让集群按一个已经不在的成员
  算多数派。
- 「不是 leader」「上一次还没提交」「没有多数派」都是 503；「已经是成员」
  「不是成员」「移除最后一个」是 409。
